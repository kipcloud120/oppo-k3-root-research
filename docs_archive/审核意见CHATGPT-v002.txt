一、Wi-Fi 路线：我发现新版静态分析存在一个关键逻辑漏洞
这是我本次复评最重要的发现。

先看作者这次确认的真实调用链：
1. shell UID 2000 可以通过 app_process 使用正确的 Binder 接口描述符。
2. wifi 服务将事务 10070 转发给 OPPO helper。
3. helper 没有 getCallingUid() 权限门禁。
4. 调用进入 root 身份的 Wi-Fi HIDL 服务。
5. HIDL 服务把参数交给 executeDriverCommand()。
6. native 层选择不同命令分支，然后使用 sh -c。
这些环节目前都有相应证据。
GitHub+1

1. 真正的问题在 myftm 分支
新版 WIFI_P0_PARAMETER_TRACE.md 给出了如下反汇编结果：
append("/vendor/bin/myftm", 17);
append(input_after_prefix);
execv("/vendor/bin/sh", {sh, "-c", cmd});


作者还明确确认：
- myftm 分支不调用 sub_9f64。
- 不经过已经发现的 regex 黑名单。
- 参数被直接追加到固定命令路径。
- 最终交给 /vendor/bin/sh -c。

GitHub+1
作者据此认为：
参数只是固定路径后面的一个 token，无法逃离 myftm 命令。

我认为这个推论不成立，至少当前报告没有证明它成立。

原因是作者混淆了 shell 的普通参数分隔与 shell 控制操作符。

举例来说，空格可以把路径后面的内容变成程序参数，但 ;、|、&& 等字符属于 shell 语法操作符。Shell 即使不遇到空格，也会识别未引用的操作符并进行语法解析。

POSIX Shell 语法对此有明确规定。
dejavu.org+1


因此：
- 将输入追加到固定可执行文件路径，不等于安全。
- 不经过 regex，反而意味着这条分支没有使用前述黑名单。
- 最终使用 sh -c，使字符串会经过 shell 语法解析。
当然，这还不能直接证明可以成功提权，因为还需要排除其他位置存在的统一过滤、转义、引号封装或输入规范化。

但我认为，v2.9 没有证明这些保护机制存在，就直接判定 myftm 分支不存在命令注入，是一个重要的审计缺口。

三、GhostLock：没有出现新的突破
目前仍然是原来的结论：
- 三条 xattr 写栈候选已经找到。
- 栈槽复用已经通过静态分析。
- NUL 截断已经通过静态分析。

所以 GhostLock 当前缺的是内核信息泄露，而不是继续调节竞速参数。

六、我的最新最终结论
Conditional GO
项目应继续，但只针对 Wi-Fi myftm 分支做一次有针对性的复审。

目前尚无 ROOT 成功证据，也没有足够证据宣布该分支一定可以提权。

但 v2.9 的关键 NO-GO 推理存在一个尚未解决的 shell 解析问题，因此我不接受它将 Wi-Fi P0/P1 全部关闭的结论。

最终状态：没有成功提权；Wi-Fi 服务链已触达 root；myftm 分支的输入安全性仍未得到充分证明。

我建议作者下一次更新不要再增加一批 CVE，也不要急着上机注入。先把 myftm 分支的完整字符串构造和过滤路径审计清楚。

具体需要证明三件事：
1. input[5:] 在追加前有没有任何全局字符过滤。
2. 最终传给 sh -c 的字符串有没有正确引用、转义或参数隔离。
3. 是否存在 shell 控制操作符被解释为命令语法的可能。
如果确认不存在统一过滤和正确转义，那么这条路线就不应该继续标记为 NO-GO，而应当重新列为高优先级漏洞候选。若证明存在可靠的转义或过滤，才能关闭它。
