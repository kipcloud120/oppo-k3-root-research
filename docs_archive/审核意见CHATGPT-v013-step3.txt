我认为阶段 3 是 K3 项目目前最需要谨慎处理的阶段。因为刚获得 KASLR slide，很容易产生一种错觉：最困难的地址问题已经解决，GhostLock 就快成功了。

实际上，这次突破消除了一个地址障碍，但没有消除 GhostLock 最核心的对象地址约束。

我重新对照了项目的 DUMPSTATE_KASLR_PATH.md 和 WAITER_ADDRESS_ANALYSIS.md。建议把阶段 3 设计为一个有明确判断门槛的专项研究，而不是马上恢复完整 PoC。
一、首先明确阶段 3 真正要解决什么
目前有四类地址信息：
类别	内容	最新状态
① A	Kernel Image Mapping / KASLR slide	已取得
① B	Direct Map / mm_struct	已验证
②	有效、可控的 rt_mutex 对象地址	未解决
③	持有 stale waiter 的 W 线程栈地址	未解决

这里有一个重要的技术判断。

K3 的 GhostLock 不只是需要某个非零内核指针。项目的源码分析已经确认，rt_mutex 的 lock 会被实际解引用，并涉及内部状态和对象关系检查。

因此，真正需要的是：

一个有效、内核可访问、结构合法，并且生命周期符合研究前提的 rt_mutex 对象。

普通内核地址、KASLR slide、Direct Map 基址都不能自动满足这个要求。

三、优先事项 P1：重新审视 ② 和 ③ 的关系
阶段 3 的核心
我认为这里最重要的工作不是寻找更多地址，而是先确定到底需要哪一种地址。

WAITER_ADDRESS_ANALYSIS.md 中已经将可能的合法对象地址来源分成两类。
方向 A：W 线程内核栈地址
K3 现有载体最直接的地址缺口
当前 xattr 栈载体与 waiter 所在的内核栈有关。

已经完成的工作：
- waiter 的结构布局已从 4.9 源码确认。
- 栈帧几何关系已有静态分析。
- 已确认目标是持有 stale waiter 的特定线程，不是任意线程。
尚未解决：该 W 线程的实际栈基址没有可靠来源。
GitHub+1


方向 B：现有合法内核锁对象
替代研究方向
分析报告指出，合法的 pi_state 内部包含 rt_mutex，理论上可以作为对象地址来源。

但目前缺少该对象的独立定位证据，KernelSnitch 得到的 mm_struct 地址不能代替它。
GitHub


我的建议是：先比较两种路线在证据要求、适用条件和设备兼容性上的差异，不要预先决定一定要追踪 W 线程栈。

这样可以避免对一个难以观测的地址来源投入大量时间，却忽略等价的对象地址研究方向。
四、优先事项 P2：不要把 SP 泄露误当作 W 线程栈泄露
这是 dumpstate 新成果中最容易被过度解读的部分。

项目的早期 WARNING 确实输出了：
- PC
- LR
- SP
- 其他通用寄存器
但已确认的 SP 属于启动期间的 init/swapper 执行上下文，不是 GhostLock 中持有 stale waiter 的 W 线程。
GitHub+1


因此，我建议对今后的地址信息采用严格分类：
观察到的内容	能证明什么	不能证明什么
PC/LR	当前 boot 的代码地址	目标对象地址
.text slide	内核镜像运行时位置	内核堆布局
Direct Map 地址	某个对象的线性映射位置	其他对象的具体地址
某个线程的 SP	该线程的栈地址信息	另一个线程的栈地址

尤其是最后一项：同一个进程的不同线程具有独立的内核栈。

这个区分应该成为 v13 阶段 3 的强制审计规则。
五、优先事项 P3：重新评估 KernelSnitch 的实际价值
这里我建议改变对 KernelSnitch 的定位。

此前它最主要的成果是恢复 mm_struct 的线性映射地址。

现在又有 dumpstate 提供的 KASLR slide，KernelSnitch 的价值已经不再是弥补内核镜像基址缺失，而是保留为独立的 Direct Map 地址观测工具。

不过项目已有的源码分析确认：
- futex 哈希键包含用户地址、mm_struct 或 inode 等信息。
- 内核栈地址不在 futex key 中。
- mm_struct 与线程栈属于不同分配来源。
- 两者在同一线性映射区域，不代表有确定的地址关系。
因此，不建议继续把 KernelSnitch 扩展成栈地址定位工具。
GitHub


原 M2 固定时间邻接路线也继续冻结。 新的 KASLR slide 不会自动修复之前已经被真机示踪否定的地址预测模型。
六、优先事项 P4：建立明确的证据验收标准
我建议今后阶段 3 的每个新结论都必须通过以下四项审核：
验收项目	合格标准
地址归属	明确属于内核镜像、Direct Map、堆对象还是特定线程栈
时间归属	能绑定对应 boot ID 和内核构建
对象身份	不只是一个看起来合法的地址，而是有独立证据确认对象类型
生命周期	对象在被观察时确实有效，不能把已经释放或复用的地址误当成活对象

另外要区分：
- 静态源码证明；
- 精确固件反汇编证明；
- 离线数据推导；
- 真机运行时观测；
- 独立交叉验证。
这五个证据等级不能相互替代。

我不建议在这一阶段继续制造新的内核竞态、强制触发异常或编写完整提权 PoC。对于 K3 这种老版本内核，误判对象生命周期可能直接导致设备 panic。

最终建议
我给阶段 3 的核心建议归纳成三句话：
1. KASLR slide 已解决，不要再把它当成主要研究瓶颈。
2. 不要追求任意内核地址，而要区分目标对象的类型、归属和生命周期。
3. 优先确认 GhostLock 的真实地址依赖，再决定研究对象栈还是现有锁对象，避免两条路线同时盲目投入。
阶段 3 的成功标准
不是获得一个新的内核地址，而是找到一个有独立证据支持的地址来源，能解决 GhostLock 当前尚未满足的具体前置条件。

如果没有这种证据，正确的阶段性结果就是继续 NO-GO，而不是强行恢复 PoC。

最后，我认为阶段 3 应该与 WLAN 驱动审计保持并行。不要因为 GhostLock 刚取得 KASLR slide，就暂停已经有实际调用入口的 WLAN 研究。
