三、P1：完成 WLAN hdd_driver_command 调用链审计
v13.2 第一主线
这是我最建议投入的方向。

它有三个优势：
1. 已经有完整的 F.16 WLAN 驱动模块。
2. 已经确认驱动入口和参数边界。
3. 已有受限 UID 0 执行主体，能够绕开普通 shell 的部分权限限制。
但是，最重要的调用连接点尚未被证明。

R1 报告指出：
- 0x89f1 进入 hdd_driver_command。
- 有固定长度输入。
- 有 0x2000 长度上界。
- 有显式 NUL 终止。
- 有 98 项命令白名单。
- 未匹配命令返回 ENOTSUPP。
- 现有释放路径均经过 __qdf_mem_free。
但 /odm/bin/iwpriv 或其他用户态工具与这个内核 ioctl 的最终绑定还未确认。
GitHub+1


我建议将这一任务拆成四个子阶段。
P1-A：确认用户态到内核态的连接关系
首先恢复和核对 PCGM00 F.16 中的用户态工具。
检查对象	需要回答的问题
/odm/bin/iwpriv	实际使用哪些 ioctl 命令
Wi-Fi HAL / 私有接口	是否存在调用同一驱动入口的路径
executeDriverCommand	是否真的经过 hdd_driver_command
hdd_ioctl	驱动分派路径是否与 F.16 模块一致
SELinux	oplus_wifi_service 是否有实际打开设备和执行相关操作的权限

这里特别建议优先从 F.16 官方固件物料中离线提取用户态二进制，不要因为设备实时访问被 SELinux 拒绝，就放弃这条研究线。
关键验收条件
只有形成明确的：

用户态调用方 → 系统调用接口 → 驱动 ioctl 分派 → hdd_driver_command

证据链，才能宣告调用连接闭合。

仅仅发现相同的字符串、函数名或者 ioctl 常量，不足以证明调用关系。
P1-B：审计 98 个命令消费者
这一步比继续寻找新的长度溢出更有价值。

既然入口的基本长度边界已经确认，接下来应关注命令分发到具体消费者之后的安全属性。

建议将 98 个 handler 分类：
类别	审计重点
参数解析	字段类型、边界、数值范围
内存管理	分配大小、对象所有权、释放路径
状态管理	状态转换及错误回滚
并发管理	锁、回调和异步操作的生命周期
外部交互	驱动、固件、诊断组件之间的数据边界

每个 handler 都应有一行审计记录：

入口 → 参数来源 → 长度约束 → 对象生命周期 → 状态变化 → 错误出口

不要因为白名单存在，就认为全部 handler 安全；也不要因为某个 handler 使用了内存分配，就直接将其认定为候选漏洞。

这一阶段的目标是找到具体违反的不变量，而不是凑出一个漏洞数量。
P1-C：判断独立的安全价值
审计完成后应该有三种可能结论：
- 调用链不存在：关闭该调用路径。
- 调用链存在，但参数和生命周期均符合预期：关闭该候选。
- 存在明确的静态安全缺陷：形成独立报告，记录影响范围和触发前提，再考虑是否有必要进入经过单独授权的安全验证。
当前设备不建议直接进行未知驱动命令的动态输入测试，尤其不要让研究过程影响 Wi-Fi 服务和现有受限 UID 0 通道。
P1-D：确认是否存在实际的受限 UID 0 代理路径
这里需要特别区分两件事：
- oplus_wifi_service 的 capability 和 SELinux 域满足驱动层的权限条件。
- 这个进程实际上是否调用了目标 ioctl。
前一项已有证据，后一项仍未闭合。不能用前者代替后者。
