三、Wi-Fi 可写面消费者：我认可本次的主要否证结论
报告：

WIFI_DATA_CONSUMER_AUDIT.md

这是本次最有价值的第二项更新。

此前我们最担心的是：
root Wi-Fi 服务可以写入配置文件，而其他高权限服务可能读取并执行这些数据，从而形成跨 SELinux 域提权。

v2.16 把这条路线拆成三个条件：
1. 能否连接到目标服务？
2. 能否使目标服务执行自己控制的代码？
3. 能否让目标服务重新读取受控数据？
作者发现，这三个条件在当前设备上都存在阻断。
1. 最重要的两个实例被排除
服务	本机实际配置	结论
wpa_supplicant	没有 -c 配置文件参数	不会按预期读取我们写入的配置文件
hostapd	没有 -c 配置文件参数	同上
fstman	虽有 -c /data/vendor/wifi/fstman.ini 的配置记录，但本机未运行	当前不可达

此外，两个可写文件类型上没有任何域持有 execute 授权。

因此，不能用传统的“写入恶意 so，再等高权限进程加载”方式实现提权。
GitHub+2

2. 一个更关键的发现：Binder 跳板方向反了
作者比较了各消费者域的 Binder 权限。

结果是：在其审计的这些消费者域中，唯一具有 system_server Binder 调用权限的是 oplus_wifi_service 本身。

报告中的权限关系
oplus_wifi_service

UID 0 / 受限 root
可调用 system_server

自身具有 Binder 调用权限
其他 Wi-Fi 消费者

UID 1010 / 1000 等
没有 system_server Binder 通道

这里比较的是报告列出的文件消费者域，并非全系统所有 SELinux domain。

所以作者提出的结论是：

即使某个低权限消费者出现代码执行，也不一定能够利用 system_server 取得比当前 Wi-Fi 域更高的系统权限。

这个推论在目前列出的服务集合内是合理的。
GitHub+1

3. 但我发现一个重要残留攻击面
这里是我对 v2.16 最主要的独立补充意见。

报告证明：

oplus_wifi_service 具有向 system_server 发起 Binder 调用的 SELinux 权限。

但这并不等于已经审计完了 system_server 接口本身。

Binder 的 SELinux 授权解决的是进程之间能否通信；具体服务是否允许调用者执行某个操作，还取决于 Java/native 服务层自己的权限和身份检查。

因此，以下问题仍值得研究：

oplus_wifi_service 以 UID 0 发起的 system_server Binder 请求，实际能够调用哪些服务方法？

特别需要区分：
- 只允许查询状态的接口；
- 通过 checkCallingPermission() 限制的接口；
- 依赖 UID 1000 判断的接口；
- 可能以调用者 UID 0 触发系统管理操作的接口。
这不是说这里已经存在漏洞，而是 v2.16 的消费者分析没有等于完成了 system_server 全部 Binder 方法的权限审计。

我会将其登记为一个独立于文件消费者的待审攻击面。

四、我发现了一个可能影响消费者审计可靠性的关键问题：atoll 与 SDM710
这是本轮最值得作者补充说明的取证问题。

报告 §26.3 将 K3 的目标机型称为 atoll，并据此判断 fstman 没有服务定义。

但是项目自身设备基线明确记载：
- OPPO K3 PCGM00
- SoC：Snapdragon 710
- CPU 平台：SDM710
而 Android Qualcomm 平台资料通常将 atoll 对应 Snapdragon 720G / SM7125。
specdeviceinfo+1


所以我认为这部分存在潜在的目标匹配问题。

需要注意，厂商构建系统可能给共同配置使用不同的内部命名，因此不能仅凭 SoC 名称直接认定文件选错。

但必须有证据说明：

atoll 对应的 init rc 确实是这台 PCGM00 F.16 实际采用的那一组配置。

否则，关于 fstman 未部署、实际消费者集合和高权限读取者的判断，仍然存在覆盖缺口。

作者自己也把 G-W4 登记为尚未逐份确认 SDM710 生效 rc。

五、GhostLock：仍然不值得恢复主线
v2.16 没有解决 GhostLock 的核心问题。

现有条件：
- 三条 xattr 栈覆盖候选成立。
- waiter 栈槽复用成立。
- NUL 截断不构成阻断。
- fake waiter 所需的内核地址仍不可获得。
- Wi-Fi 受限 UID 0 也不能读取必要的内核地址信息。
所以我仍然建议冻结。

不过我不完全接受 DIAG 报告中更广泛的表述：

“即使 DIAG 存在内存破坏，也因为缺地址而不能利用。”

这只能对依赖伪造内核指针的利用链成立，不能无条件推广到所有内存安全漏洞类型。比如不依赖已知内核地址的数据破坏或特定控制流原语，在理论上有不同的利用前提。

因此，准确表述应该是：

现有 GhostLock 利用链及依赖有效内核指针的路径被地址泄露问题阻断；DIAG 新发现的其他漏洞不能仅凭这一点预先判死。

这一点也与作者将 DCI 解析树列为未审计内容相吻合。
