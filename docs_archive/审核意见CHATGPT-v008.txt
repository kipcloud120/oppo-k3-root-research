4. 我发现还需要进一步核实的一个技术口径
这次审阅中，我认为有一个地方应该再收紧。

README 和部分报告将 KernelSnitch 的结果概括为：
mm_struct 线性地址 / KASLR slide / DPM 基址。

但这三种概念并不完全等价。

ARM64 内存布局中，线性映射使用 PAGE_OFFSET、PHYS_OFFSET 进行虚拟与物理地址换算；内核镜像的映射则使用 kimage_vaddr、kimage_voffset，KASLR offset 由内核镜像虚拟地址相对于固定基址计算。两套映射需要分别分析。
Git at Google+1


所以：
- 泄露 mm_struct 线性映射地址，确实是有价值的内核地址泄露。
- 它能够帮助确定相应线性映射区域的内存位置。
- 但不能仅凭一个 mm_struct 地址，就直接断言内核 .text 的 KASLR slide 已经被完整恢复。
FEASIBILITY_v007.md §12.1 对两者之间的推导有一个需要补证的步骤。我建议项目进一步区分 DPM 地址定位、物理地址转换、内核镜像 KASLR slide，给出独立的数学关系和反汇编证据。

这不否定 KernelSnitch 已经取得的结果，但能避免把一种内核地址泄露夸大成另一种地址泄露。
GitHub+1


还有一个统计验证问题值得注意：项目自己发现原参考实现对多个 hashsize 使用 OR 判定，会使误报率受最小 256 桶配置主导。它估算 N=4 时全窗口误报期望约 0.65，并建议采用单独 1024 桶判定或提高独立碰撞数量。真机探针的 110× 信号证明时序 oracle 存在，但还应与这一唯一性问题分别看待。

6. 我对下一阶段的建议
我会将 v3 后的研究重点重新排列：

第一优先：验证堆地址路线的可行性边界。

重点不是重复验证 futex 计时，而是审计 K3 是否已经具备可控的内核堆对象分配与生命周期条件。PCKM00 的 AF_UNIX skb 路线是对照案例，但不能直接假定 K3 的内核分配器行为相同。

第二优先：重新审计线程栈地址泄露。

重点是确认 !VMAP_STACK 设备上有哪些与栈页位置有关、又能从低权限观察到的机制。已有 futex 哈希侧信道不包含栈地址，不能重复用它来论证栈地址可得。

第三优先：收紧地址泄露结论。

把 DPM、mm_struct 地址和 text KASLR slide 分开验证，避免后续利用链依赖一个尚未充分证明的基址。

暂时不建议重新投入 boot_id 回读和 ashmem_fops 地址来源研究：项目的源码分析已经表明，前者依赖既有内核写原语，后者主要用于验证已经获得的地址。它们不是当前缺口的独立起点。
GitHub+1


最终结论
v3.0：研究突破，尚未提权
我对这次更新的评价是：从“没有地址线索”推进到了“已验证一种内核地址侧信道，但尚未取得 GhostLock 所需的目标对象地址”。

这是实质性进步，而不是换个说法继续 NO-GO。

但当前距离可用临时 ROOT，仍然隔着一个关键障碍：需要让 fake waiter 指向可控、合法的内核锁对象，或者取得精确的当前内核栈地址。

建议把以下文件作为 v3 的主要审阅入口：
- v3 接手摘要 HANDOVER_RESUME.md
- GhostLock 地址约束分析
- KernelSnitch 本机验证
- 真机探针结果
- v3 最终分层判定
一句话：v3 让我重新认真看待 K3 的 GhostLock 路线，但我还不会把它评为“接近 ROOT 成功”。现在最重要的不是再证明能拿到一个内核地址，而是证明能否得到 GhostLock 真正能使用的那个内核对象地址。
