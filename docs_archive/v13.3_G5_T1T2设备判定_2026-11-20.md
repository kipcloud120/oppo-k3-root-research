## 2. T1：mm slab 页是否真的回到 buddy

### 2.1 方法

- `fork` N 个子进程（每个 `copy_mm` 分配 1 个 mm_struct；父/子绑 CPU0）；
- E1：全部 kill → 看 `mm_struct slabdata` 回落；
- E2：每 18 个先 kill 1 个（seed）再 kill 其余 → 看是否优于 E1；
- E3（A17 式）：保留第 18 个为 "leak 代理"，先 kill 其余 575/1151 个，最后 kill leak → 看 leak 最后退出时 `slabdata` 是否恰好 −1（即 leak 页 slab 被丢弃）。

设备基线：`mm_struct 896 B × 18/slab，order-2`，`slabdata` 20–30（随系统进程波动）。

### 2.2 结果（原始输出摘录）

| 实验 | fork 后 slabdata | kill 后 slabdata | 丢弃数 | 备注 |
|---|---|---|---|---|
| E1 mass-free（576） | 52（936 obj） | **30（540 obj，437 active）** | **22/32** | 保留 8 个 partial slab（含 ambient mm） |
| E2 seed+mass-free（576） | 52（936 obj） | **28（504 obj，437 active）** | **24/32** | seed 略优 |
| E3 pre/leak/post（576，#1） | 52（936 obj） | 32（576 obj，439 active）→ **31（558 obj）** | 20 + **1** | **leak kill 后恰 −1** |
| E3（576，#2） | 52（936 obj） | 30（540 obj，438 active）→ **29（522 obj）** | 22 + **1** | 复现 |
| E3（1152，#3） | 84（1512 obj） | 35（630 obj，510 active）→ **34（612 obj）** | 49 + **1** | 复现 |

> 三次 E3 中，**"最后 kill leak 代理"这一步都恰好使 `slabdata` 减少 1**：leak 所在 slab（前 17 个 pre 填满 + leak 第 18 个）在 leak 退出时变空，且此时 node partial ≥ `min_partial=5`，触发 `discard_slab → __free_pages(order=2)` 回 buddy。**这是"目标页可被释放"的设备级证据（针对 leak 页本身）。**
> 保留的 30–34 个 slab 是**部分占用**（有 ambient 进程的 mm 混入），不是"空 slab 未丢弃"；空 slab 丢弃机制本身成立。

### 2.3 判定

**T1 通过**：4.9 SLUB 的空 slab 丢弃路径在本机可达；A17 式 kill 顺序能把 leak 页的 slab 精确释放到 buddy。离线模型（`min_partial=5`、`cpu_partial=13`、seed 必要性）与实测一致。

## 3. T2：dgram 16064 喷射是否稳定拿到 order-2 页

### 3.1 方法

- 256 个 `SOCK_DGRAM` socketpair，`SO_RCVBUF=2 MB`（被 `rmem_max` 钳制），每 socket 连发 16064 字节直到 EAGAIN；
- `spray` 模式统计成功包数；`sprayhold` 模式持有 1 s，读 `MemFree` 后关闭。

### 3.2 结果

| 项 | 值 |
|---|---|
| 成功包数 | **3072 / 3072（0 fail）**，70 ms（与 v4 P1 一致） |
| MemFree（前 / 分配后 / 持有中 / 释放后） | 295 600 / 232 872 / 232 592 / 295 156 kB |
| 净占用 | **−62.7 MB**（≈3072 × 16 KB = 48 MB payload + skb 头等） |

### 3.3 判定

**T2 通过**：16064 字节 dgram 确实走单块 order-2 页（与离线推导一致），且可稳定分配/持有/释放 3072 页。`/proc/buddyinfo` 对 shell 不可读，故无法直接看 order-2 计数；MemFree 的 62.7 MB 净占用与 3072 页量级一致。

## 5. 下一步：T3（需单独授权，风险明确）

**T3 设计（概要）**：KernelSnitch 泄露 leak child 的 mm → 计算页基址 → E3 groom 释放该页 → 立即 dgram 喷射写入 fake lock/decoy → W 的 xattr fake waiter 指向 fake lock → `sched_setscheduler(W)` 触发链 → 用 **8 字节零写**落到一个 shell 可读的静态 sysctl（候选 `kptr_restrict`），读回 0 即证明页级复用 + 写原语。

**风险（必须明示）**：
- 若该页**不是**我们的（喷射未命中/被抢占），`:702` 读 `lock->waiters_leftmost` 会命中非预期内存 → **fault/panic → 设备重启**；
- 重启会**作废当前 boot 的 KASLR slide 证据**（`KASLR_EVIDENCE.md`，boot `b9f9f06a-…`），并违反迄今"不重启"的硬约束；
- v0132 §六的设备安全边界明文要求"不在当前设备制造新内核竞态或强制异常"；T3 属于必须单独、逐次授权的例外。
- 备选：先做**无触发的弱验证**（KernelSnitch 双 leak：释放后新 mm 是否落在 leak 页），只能证"页已释放"，不能证"skb 复用"；T3 是唯一直接证据。

**在获得明确授权前不执行 T3。**

## 9. 页级释放判定（reclaim_ks，安全，未触发 GhostLock）

用 `live_probe/reclaim_ks.c`：KernelSnitch（ksnitch_k3）泄露 leak child 的 mm → E3 式 kill（pre/post 先杀、leak 最后）→ 再跑 4 个 probe 的 KernelSnitch，比较其 mm 页与 L。

| 项 | 值 |
|---|---|
| leak mm / 页 L | `ffffffc5efd68380` / `ffffffc5efd68000`（offset 0x380） |
| probe #0–#3 mm 页 | 全部 `ffffffc5efdd8000`（对象偏移 0x0e00/0x1180/0x1500/0x1880，顺序递增） |
| 判定 | **UNKNOWN**（新 mm 没有落回 L；mm cache 继续使用另一个 partial slab） |

**解读（不夸大）**：
- 该结果**不否证**"L 页被释放"：mm cache 优先使用其 current/partial slab（`0x...dd8000` 这页还有空槽），不会立刻向 buddy 要新页；L 可能已被 discard 但未被 mm 复用。
- 也不能证明 L 被释放：leak child 的 slab 页可能混有 ambient mm 对象（pre 17 未与 leak 对齐），未必变空。
- **页级复用的唯一直接证据仍是 T3**（触发链 + 写原语），而 T3 在页不匹配时会 `:702` fault → panic/重启。是否执行 T3 需单独确认。

## 10. T3 载体裁决：必须换用 raw-byte 栈载体（pselect），xattr 不可行

结合 `GHOSTLOCK_NUL_ANALYSIS.md`（§2.3/§4/§6/§7）与本轮拿到的 heap 页地址，T3 的 fake waiter 字段约束如下：

| 字段（waiter 偏移） | T3 需要 | xattr `strncpy_from_user` 能否满足 |
|---|---|---|
| `tree.__rb_parent_color` (0x00) | `Q = target-0x10`（本机 `ffffff995b80eba8`，全字节非零） | ✅ |
| `tree.rb_right` (0x08) | `V`（可写地址，如 `L+0x888`，可选全非零） | ✅（选页内偏移避开 0） |
| `tree.rb_left` (0x10) | **必须为 0**（走单子节点 `rb_erase` 路径） | ❌ **0x00 会截断串**，后续字段全废 |
| `pi_tree` (0x18–0x2f) | 任意非零（不被读） | ✅（填非零） |
| `task` (0x30) | 任意非零（本路径不解引用） | ✅（填非零） |
| `lock` (0x38) | `L+0x40`（本页 fake lock） | ✅（L 低字节 0x40，非零） |
| `prio` (0x40) | ≠120，如 130；可由终止 NUL 落在 prio+1 自动补零 | ✅ |

⇒ **`rb_left=0` 与 NUL 语义直接冲突**：这不是参数问题，而是 xattr 载体的语义边界。`GHOSTLOCK_NUL_ANALYSIS.md` §7 已把"raw-byte 栈载体（`__copy_from_user` 族，无 NUL 语义）"列为 GhostLock 的重开条件②；A17/NebuSec 公开链用的正是 **pselect（`stack_fds` fd_set，raw bytes）**。

**因此 T3 的正确路线是**：
1. 离线求出 K3 上 `do_futex`/`futex_wait_requeue_pi` 的 waiter 槽与 `core_sys_select` 的 `stack_fds` 缓冲之间的栈深度差（与 `getxattr` 的 boff 同法）；
2. 用 pselect 的 3×fd_set 原始字节把 0x50 B fake waiter 写到该槽（含 `rb_left=0`）；
3. `sched_setscheduler(W)` 触发；用 8 字节零写落到 `kptr_restrict` 验证（成功=页级复用+写原语成立；失败=`:702` fault/panic）。

> 这一步的失败代价是设备重启与当前 boot slide（`0x1953600000`）作废；在完成 pselect 几何与 payload 校验前不触发。

## 11. 更正（同日）：xattr 并非不可行——改用 rb_erase 的"两子节点 Case 2"路径，waiter 全字段非零

§10 的结论（"必须 pselect"）基于"单子节点路径需要 `rb_left=0`"；但 4.9 `__rb_erase_augmented` 对**两个子节点**有 Case 2 路径，可在**所有 waiter 字段非零**的前提下完成可控写，且零值只出现在**我们控制的 skb 页内容**里（raw 字节，不受 NUL 约束）：

```
fake waiter:  parent_color = Q        (kptr_restrict-0x10, 全字节非零)
              rb_right     = V        (L+0x888, 全字节非零)
              rb_left      = V2       (L+0x988, 全字节非零)
页内内容:     V+0x10 = 0   (Case 2 判据 child->rb_left == 0)
              V+0x08 = V2  (child2 非零，避免 __rb_erase_color(NULL))
              V、V2 均在页内，可写
```

`__rb_erase_augmented` Case 2（`lib/rbtree_augmented.h`）：
1. `tmp = child->rb_left` = 0 → Case 2；
2. `child2 = successor->rb_right` = V2（非零）；
3. `successor->rb_left = V2`；`rb_set_parent(V2, V)` → 写 V2+0；
4. `__rb_change_child(node, successor=V, parent=Q, root)` → **`*(u64*)(Q+0x10) = V`**（目标写；Q+0x10 = kptr_restrict）；
5. `child2` 非零 → `rb_set_parent_color(V2, V, BLACK)` → 写 V2+0；`rebalance=NULL`，**不进入 `__rb_erase_color`**。

⇒ **xattr 载体可行**：waiter 0x00–0x50 全字节非零（`task` 填任意非零；`lock=L+0x40` 非零），末尾在 prio 后以 NUL 终止（prio 高位由 `strncpy_from_user` 的 zero-mask 补 0；deadline 不被读）。这正好落在 `GHOSTLOCK_NUL_ANALYSIS.md` §2.3 的 boff 表（fgetxattr boff=0x10，串长 81）之内；**不需要 pselect**。

### 11.1 修正后的 T3 组装

1. KernelSnitch（已通）→ leak child mm → L；
2. E3 groom（pre 先杀、leak 最后）→ L 页 discard；dgram 16032/16064 喷射 → 页内 fake lock（+0x40）/ decoy（+0x200）/ V/V2 节点；
3. W 线程经 g1 三锁环得到悬垂 `pi_blocked_on`；W 调 `fgetxattr(fd, name=<81B payload>, ...)` 覆盖 waiter 槽；
4. 主线程 `sched_setscheduler(W, SCHED_NORMAL, 0)` → 链走查 → `*(kptr_restrict)=V`（V 为页地址，非零指针；若要 8 字节零写，可把 V 改成 0 但 NUL 又冲突——**指针写即可验证**：读 `kptr_restrict` 会得到非零页地址值，仍可判成功）。

> 剩余风险：L 页是否被 skb 取到、fgetxattr 的栈深度是否精确落槽、payload 字段/页内容是否自洽。任一不满足 → `:702`/rb_erase fault → panic。首次触发前应把 payload 与几何做离线自检；是否执行触发仍由用户最后确认。

### 12.2 直接归因

1. **Carrier NUL 截断（已定位并修复）**：L=`ffffffd9df010000` 时 `L+0x40` 的第二字节为 0x00，`strncpy_from_user` 在 0x49 截断，fake waiter 的 `lock` 变成 `0x40` → `raw_spin_trylock(0x40)` fault。修复：运行时选 `lock/V/V2` 的页内偏移，保证 8 字节全非零（v2 的 `pick_offsets`；随后 carrier 校验 81 B 全非零）。
2. **空 slab 未 discard（已定位，未完全解决）**：仅 warm 576 时 leak kill 前后 `slabdata` 不变（32→32、34→34）；加 "5 个 partial keeper + 杀 leak 后 flush keepers" 后出现 47→43 的下降，但**不能证明 L 本身在下降的 4 个 slab 中**。panic 仍复现。
3. **X 合法 top waiter 不是安全网（已证伪）**：`T3_NOCARRIER=1`（不调 fgetxattr）在同一拓扑下仍然 panic。说明"carrier 未命中 → W->pi_blocked_on 仍指 C 的旧 waiter → 链走 C（X 为 top）"这条路径本身会 fault，不能作为 fallback。因此**carrier 未命中与 L 页未取到都会 panic**，二者无法用该拓扑区分。

### 12.3 当前判定

- T3 目标（页级复用 + 写原语）**未证明**；`boot_id` 未被写坏（每次都因 panic 重启）。
- 四层判定不变：**可用 ROOT / 持久 ROOT NO-GO**；GhostLock 仍冻结（v0132 §六）。
- 继续盲目触发只会反复重启，且每次需 4–5 min 的 dumpstate 才能恢复 slide；应先补一个**页身份 oracle**（证明 L 确实被 discard 且被 skb 取到）或改用可验证的 SLUB discard 策略，再触发。

## 13. 页身份 oracle + carrier 几何独立复核（2026-11-20 20:00–20:15，安全，无触发）

### 13.1 Carrier 几何：独立从反汇编复核，确认 boff=0x10 正确

- `SyS_fgetxattr` @0x8270740：帧 0x40（`stp x29,x30,[sp,#-0x40]!`），调用 `getxattr` @0x8271408。
- `getxattr` 帧 0x150，`kname` 缓冲在 `sp+8` ⇒ 缓冲绝对偏移 = 0x40 + 0x150 - 8 = **0x188**。
- futex 侧：`sys_futex` 帧 0x70 + `do_futex` 帧 0x1f0；`futex_wait_requeue_pi` 内联在 `do_futex` 内，`rt_waiter` 在 `x29-0xa8`（`x29=sp+0x190`）⇒ `sp+0xe8` ⇒ 绝对偏移 = 0x70+0x1f0-0xe8 = **0x178**。
- ⇒ waiter = buffer + (0x188-0x178) = **buffer + 0x10**，与 `gl_nul_analysis.py` 的 fgetxattr boff=0x10 完全一致。**carrier 偏移没有错**；第 4 次定位的 NUL 截断是唯一载体 bug，已修。

### 13.2 页身份 oracle（T3_PAGECHECK）

做法：groom 后（warm 576 + pre 17 + leak + post 18 + 90 anchor/360 flush 代理；杀 leak → flush）先吃光 mm cache 的空闲对象，再 fork 一个 probe 跑 KernelSnitch，比较其 mm 页是否 == L。

| 运行 | 配置 | L | probe 结果 |
|---|---|---|---|
| #1 | 90 keepers + 5 partial | fffffff1fe8d4000 | probe page fffffff2b1bc8000 ≠ L |
| #2 | 360 keepers + 20 partial | fffffff25d0b0000 | 只有 1 次 probe（旧二进制），≠ L |
| #3 | 90 anchor（永久 partial）+ 360 flush | fffffff1cfb48000 | 3 个 probe：1cfb48000 / 1ce9f8000 / 1d6710000，**均 ≠ L** |
| #4 | 同上（anchor 版） | fffffff1cea88000 | 3 个 probe：1cfb48000 / 1cfaf8000 / 1cfaf8000，**均 ≠ L** |

- `slabdata` 确实下降（#3 61→39、#4 61→39），说明 flush/discard 在发生；但 **L 没有被任何 probe 的新 slab 取到**。
- 结论：**L 尚未被证明进入 buddy 空闲链**；最可能是 L 的空 slab 仍留在 CPU/node partial（或 L 并非全空），而不是被 discard。页 oracle 不能证明 L 可回收 ⇒ 此时触发必然在 `:702` 读 L 时 fault。

### 13.3 当前阻塞与下一步

- carrier 偏移/NUL 已排除；剩余唯一未决是 **L 页的确定性释放**。
- 盲触发只会重复 panic；下一步应改为"让 L 的空 slab 在 unfreeze 时被确定为 discard"或"用 mm 侧对象直接证明 L 已被复用"（例如在 flush 后强制 mm cache 连续申请多个新 slab，逐个 KernelSnitch 直到某 probe 落在 L）。
- 设备当前仍为 boot `7a818860-…`（页 oracle 全程无触发，无重启）；四层判定不变。
