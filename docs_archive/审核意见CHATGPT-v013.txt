OPPO K3 项目后续工作规划：建议进入 v13 阶段
我认为这次 dumpstate 更新之后，项目应该重新调整方向。

最重要的变化是：当前 boot 的 .text KASLR slide 已经取得，GhostLock 的研究条件发生了变化，但完整 ROOT 依然没有实现。

因此，后续不应该继续把“寻找 KASLR slide”当作主目标，而应该转向两个问题：
1. 如何把新获得的地址信息转化为可验证的内核安全研究成果？
2. 除 GhostLock 之外，是否有独立的驱动漏洞路径？
我核对了 DUMPSTATE_KASLR_PATH.md §8、当前 HANDOVER_RESUME.md、HANDOVER.md、CLOSURE.md 和 README。下面是我建议的路线。

二、建议设立五条工作流
P0：dumpstate KASLR 结果固化和可复现性
第一优先级
这条路线已经成功，但还需要从一次成功实验转成可靠的项目能力。

当前问题在于：启动早期 WARNING 发生在 t<1s，而 dumpstate 需要一定时间生成报告。成功实验说明这次捕获到了所需日志，不代表每次正常运行都能保留。

我建议完成四项工作：
工作	目标
P0.1	整理当前 boot 的原始 PC/LR、寄存器证据和符号对应关系
P0.2	对原始证据和 vmlinux.elf 建立 SHA-256 校验
P0.3	区分当前 boot、历史 boot、旧 last_kmsg 的地址归属
P0.4	记录 dumpstate 的日志保留边界和成功/失败条件

特别需要记录每次取证对应的：
- boot_id
- 内核镜像 SHA-256
- vmlinux.elf SHA-256
- bootreport 采集时间
- 原始 PC/LR
- 计算后的 slide
- 地址对齐与符号偏移校验结果
这样将来即使 OTA 改动内核，也能够明确知道哪些资料已经失效。

停止标准： 当前 boot 的 slide 已经取得，符号对应和交叉验证一致，就冻结该 boot 的结果，不必重复扫描或重复重启证明同一事实。

另外建议安全发布时对原始运行时地址和完整 bugreport 做适当脱敏。公开报告可以保留方法、偏移关系、哈希和证据摘要，不一定需要公开所有运行时内核指针。
P1：研究不依赖重启的运行时内核地址来源
第二优先级
这是 DUMPSTATE_KASLR_PATH.md §7 提出的新方向。

现在已经知道：
- dumpstate 可以经 init 启动。
- bugreport 能包含内核日志。
- 内核 WARNING 能输出原始 PC/LR/SP。
- 当前 boot 的 slide 可以从这些信息计算。
那么接下来值得研究的是：当前系统运行期间，是否自然存在可观测的、不会造成设备异常的 WARNING 信息来源？

项目已经登记了 qcacld、KGSL、/dev/diag 和其他 vendor 驱动作为离线审计范围。
GitHub


我建议按以下方式研究：
子任务	主要产出
P1.1	内核镜像和已取得模块中的 WARNING 调用点目录
P1.2	各调用点的调用上下文、执行主体和参数来源
P1.3	排除会升级到 BUG()、panic 或不稳定状态的路径
P1.4	评估自然发生的运行期日志是否足够提供地址信息
P1.5	只有发现安全、明确的候选后，才考虑额外授权

我特别强调：这里先做静态审计，不主动制造内核异常。报告已经明确排除了 KGSL CVE-2023-33107 这类触发后可能直接进入 BUG() 的方向。
GitHub


这项工作有两个潜在价值：

第一，即使不再次重启，也可能获得当前 boot 的新地址证据。

第二，如果 WARNING 在不同任务上下文中自然产生，寄存器信息可能提供额外的栈地址观察线索。

但必须区分：当前已取得的 SP 属于 init/swapper，不是 GhostLock 的 W 线程内核栈地址。不能因为看到了一个 SP 就宣布 ③ 类地址已经闭合。
P2：重新评估 GhostLock，但不直接恢复 M2
核心研究线
现在 GhostLock 的前置条件发生了变化。

此前最主要的问题之一是 .text slide 不可得。现在这项障碍已经被移除。

但 GhostLock 仍然有两个关键缺口：
缺口	具体问题
②	可控、结构合法的 rt_mutex 堆对象地址
③	持有 stale waiter 的 W 线程内核栈基址

我建议把 GhostLock 分成两个独立的小课题。

P2-A：重新审查参考项目与 K3 的地址条件差异。

不要直接复制 PCKM00 项目的固定地址公式。两台设备的 SoC、内核版本、内存布局和分配器状态不同。

目标是建立一份差异报告：
- 哪些是 K3 已经确认的地址信息；
- 哪些是参考项目依赖的设备特定地址；
- 哪些是 K3 尚未观察到的对象；
- 哪些结构条件不能由 KASLR slide 推导。
P2-B：重新审查 W 线程栈地址的可观测性。

新发现的 WARNING 寄存器输出值得研究，但只有在证明它确实对应目标线程上下文时，才有意义。

不要把 init/swapper 的 SP 直接拿来填 GhostLock 的地址需求。

这里有一个必须维持的研究纪律： KASLR slide 成功，不等于堆对象地址成功；获得一个内核地址，也不等于它是合法的 rt_mutex。

另外，v10 已经否定了 M2 的简单时间邻接固定 delta 模型。没有新的独立证据前，不应恢复同一实验路线。
P3：WLAN 驱动路线继续独立推进
第三优先级
我不建议项目把全部精力重新投入 GhostLock。

此前 R1 更正后，0x89f1 → hdd_driver_command 已成为首选离线候选。

现有分析记录包括：
- 长度上界 0x2000；
- 显式 NUL 终止；
- 98 项命令白名单；
- 未匹配时返回 ENOTSUPP；
- 各路径有内存释放处理。
但仍然缺少一个关键事实：用户态 iwpriv 与内核态 0x89f1 之间的调用绑定还没有被证实。
GitHub+1


后续应该做的是：
子任务	研究内容
P3.1	完成用户态工具与内核入口的静态调用链对应
P3.2	还原命令白名单与参数解析语义
P3.3	检查长度、状态和内存生命周期不变量
P3.4	对照已审计的 SELinux/DAC 权限模型
P3.5	判断是否存在值得进一步研究的安全缺陷

这里应严格区分“UID 0 域能访问驱动”和“已经存在一个可利用的驱动漏洞”。

在缺少完整调用链证据时，不应做动态输入测试。

这条路线最大的优势是：它不依赖 GhostLock 的堆地址原语，可以作为独立研究方向。
P4：其他 CVE 和 vendor 模块分诊
第四优先级
这条线保持低投入。

之前的 CVE-2025-38352 已经完成本机 pre-fix 形态复核，但运行时竞态条件仍未证实，而且存在较高的 panic 风险。
GitHub


因此我建议：
- 保留纯离线反汇编结论。
- 不做动态竞态 PoC。
- 不因为刚刚取得 KASLR slide，就自动升级其测试授权。
- 其他 vendor 模块先做实际加载和接口可达性盘点，再选择少量高价值对象。
项目也不应该为了增加 CVE 数量而批量移植 PoC。

三、哪些工作应该正式冻结？
方向	决定	理由
KernelSnitch M1	冻结为已验证工具	mm_struct 地址已有证据
M2 时间邻接固定 delta	继续关闭	真机示踪否证
KGSL 非 sparse 生命周期	阶段性关闭	K2 已达成
KGSL sparse KO-1	本机关闭	功能位未启用、入口不可达
GhostLock 原有固定地址移植方案	关闭	不适用于 K3 当前分配模型
FastRPC 旧路径	关闭	当前域权限集合为空
WLAN persist 配置输入	关闭	实际消费者不可达
CVE-2025-38352 动态测试	暂停	风险高、动态可达性未证

这并不是放弃这些技术，而是要求出现新证据时再重新打开。

五、建议采用明确的停止标准
这是我认为 v13 最应该强化的项目管理机制。
工作流	继续投入的条件	停止条件
KASLR	有新的当前 boot 地址观察证据	只有旧 boot 日志或静态符号
WARNING	存在明确可达且安全的候选	需要引入 BUG/panic 风险
GhostLock ②	有独立的对象地址证据	仍然依赖 M2 固定 delta
GhostLock ③	地址属于目标 W 线程	只得到 init/swapper SP
WLAN	用户态到内核接口连接得到证实	只能证明 ioctl 命令字相似
CVE	本机代码形态、可达性及安全验证条件都成立	只有外部 PoC 或 pre-fix 形态

所有设备验证继续遵循：不刷写、不解锁、不写 persist、不修改启动分区；重启需要单独、明确授权，不能把取得一次 slide 理解为获得了永久重启测试许可。

六、我认为最值得优先完成的三个成果
如果资源有限，我会这样排序：
第一
把 dumpstate KASLR 路径变成正式的取证能力

因为这是项目刚刚取得的最大突破。先把方法、证据和跨 boot 生命周期讲清楚。

第二
重新评估 GhostLock ②/③

现在 slide 已知，应该重新划定真正剩下的地址条件，但不恢复被否证的 M2。

第三
完成 WLAN hdd_driver_command 调用链审计

这是一条独立于 GhostLock 的候选路径，不应该因为 GhostLock 有了新进展而被搁置。

七、目前最容易犯的三个错误
错误一：认为 KASLR slide 已有，就等于 GhostLock 已经接近成功。

不成立。②、③仍然是不同的对象地址问题。

错误二：为了产生新的 WARNING，主动制造内核异常。

不建议。应该优先做静态审计和自然发生的日志观察，排除可能触发 panic 的路径。

错误三：继续把 HANDOVER_RESUME.md 当成最新事实来源，而不核对完整报告。

当前它仍然停留在 v12.3.1，而 dumpstate 新证据已经追加到单独报告。建议一次性统一版本和事实层级。

最终建议
我会把 v13 定义成：
v13：从地址发现转向利用条件闭合
核心目标： 不再重复寻找已经得到的 KASLR slide，而是判断新地址信息能否减少 GhostLock 剩余缺口，同时保留 WLAN 独立驱动研究路线。

第一主线： dumpstate 证据固化 + 运行期地址观察面。

第二主线： GhostLock 的 ②、③地址条件分别复评。

并行路线： WLAN hdd_driver_command 静态调用链。

维持判定： 受限 UID 0 已达成；可用 ROOT 和持久 ROOT 尚未达成。

还有一个发布管理建议：把当前真实运行时 slide 和原始 bugreport 放在受控证据归档中，公开仓库只保留必要的可复算材料和经过脱敏的摘要。这样既能让研究可复核，也能降低暴露设备运行时内核地址的风险。

我认为现在最不应该做的是急着再找一个 CVE。K3 已经有了一个真正的地址泄露原语，接下来更有价值的是搞清楚它究竟能让哪些剩余研究条件发生变化。
