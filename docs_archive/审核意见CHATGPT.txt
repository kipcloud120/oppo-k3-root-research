OPPO 私有 Binder 服务 有相关的CVE吗？


思考了 2m 10s
有，而且不止一个相关案例。 更重要的是，已经有公开 CVE 证明：OPPO 自有 IPC 服务的身份认证、权限检查和高权限操作之间，确实出现过安全缺陷。

不过要区分：有些是 OPPO 自有服务漏洞，有些是 Binder 接口漏洞，还有些只是相似的权限提升问题。不能全部称为 Binder CVE。

一、最值得关注的 CVE
我筛选出以下几个案例：

CVE-2026-22078

高度相关
OPPO O+ Connect IPC 未认证

日期：2026-06-29

CVSS：7.3 High

缺陷：IPC 服务没有认证客户端。

影响：外部应用能够通过 IPC 通道提升权限并执行敏感操作。

受影响版本：O+ Connect 16.0.33。

这是与 K3 项目计划审计的私有服务最接近的 OPPO 案例。

注意：公开 CVE 没有明确说明其 IPC 底层一定使用 Android Binder。

资料：CVE-2026-22078 详细记录 · OPPO 官方公告

CVE-2020-11829

高度相关
ColorOS Backup / Restore SDK 服务动态加载提权

日期：2020-11-19

受影响组件：com.coloros.codebook

受影响版本：V2.0.0_5493e40_200722

缺陷：Backup / Restore SDK 动态加载服务，导致权限提升。

这是一个很值得研究的 ColorOS 服务层历史漏洞。

它说明 OPPO 自有组件中的服务加载及权限边界曾出现过问题，但公开 CVE 描述没有提供足够信息证明具体利用接口就是 Binder。

CVE-2021-23244

值得检查 K3
ColorOS 11 危险权限预授予漏洞

日期：2021-12-27

影响范围：OPPO ColorOS 11 手机。

缺陷：default-grant-permissions 白名单中存在未安装的应用，攻击者可以使用相同包名伪装应用，获得危险权限。

这条尤其值得注意，因为 K3 的目标固件也是 ColorOS 11.1。

但不能因此断言 F.16 仍然存在漏洞，需要检查对应修复是否进入当前固件。

二、还有一个非常重要的旁证：OnePlus Binder 提权漏洞
值得重点参考
CVE-2026-70386（2026-10-21）

这是 OnePlus OxygenOS 的一个明确 Binder 服务漏洞。

公开技术描述指出：

atlasservice 的 Binder 接口接受 setEvent(String8 name, String8 value)。

接口缺少调用者授权检查。

事件处理函数 OplusAtlasLogWriter::handleEvent 使用外部传入的参数设置系统属性。

随后启动 root init 服务。

高权限服务最终将未经安全处理的参数传给 system()。

结果是本地应用能够借助这一缺陷链取得高权限命令执行能力。

nvd.nist.gov
+1

这不是 OPPO K3 的漏洞，也不是证明 OPPO K3 存在同样的接口。

但它非常值得关注：Oplus 系统生态中的厂商 Binder 服务确实可能存在从未认证的 IPC 调用到高权限命令执行的完整缺陷链。

四、我建议对 K3 做什么？
我会把研究重点转向以下四类静态审计：

1. Binder 身份认证

检查服务的 onTransact()、getCallingUid()、checkCallingPermission()、enforceCallingPermission()。

特别关注：普通 shell 或普通应用能否调用原本只应该开放给 system、root 或特权应用的接口。

2. 高权限操作

检查 Binder 接口是否能触发：

修改系统属性；

写入受保护文件；

启动 init 服务；

执行外部命令；

修改权限或挂载状态。

3. 服务动态加载

参考 CVE-2020-11829，检查动态加载的类、服务实现以及调用方权限是否存在错配。

4. Binder 服务与 init 之间的信任边界

参考 CVE-2026-70386，检查普通 Binder 调用能否进入高权限执行链。

不需要盲目尝试事务号，更不需要先做破坏性设备实验。

五、我的判断发生了什么变化？
此前我认为 OPPO 私有 Binder 服务是项目唯一值得投入的未知面之一。

现在有了这些 CVE 作为历史证据，我会把它提升为：

P0
OPPO 私有 Binder 服务静态审计

不是因为已经发现 K3 的漏洞，而是因为 OPPO 自身已有 IPC 服务权限缺陷的公开记录，且存在高度相似的 Android 厂商 Binder 提权案例。

其研究价值明显高于再次尝试已经失败的五条漏洞路线。

还有一个非常关键的问题：

仓库里的 10+ 个 OPPO 私有 Binder 服务，目前有没有具体服务名称、进程名和 UID 清单？

如果已经记录在 artifacts_adb/ 中，我建议下一步直接对照 CVE-2026-22078、CVE-2020-11829 和 CVE-2026-70386 的缺陷模式，做一份针对 K3 F.16 的逐服务审计清单。

这可能是这个 ROOT 项目目前最有价值的突破口。
