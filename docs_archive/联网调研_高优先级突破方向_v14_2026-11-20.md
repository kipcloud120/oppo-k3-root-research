## 0. 结论先行

1. **没有找到能够直接改变当前 NO-GO 判定的高优先级突破方向。** 四层判定不变：Wi-Fi 域内 UID 0 命令执行已达成；可用 ROOT、持久 ROOT 均 NO-GO。联网结果不能推翻本机判定（v13 第 6 节纪律第 7 条）。

2. **本轮唯一值得新登记的方向是 `CVE-2025-38352`（POSIX CPU timers TOCTOU / UAF）。** 它是全部候选中唯一同时满足「本机代码形态属于受影响分支、无 build-time 缓解、CISA KEV 在野利用、有公开 PoC」的方向。但它**不是可直接利用的突破**：公开 PoC 仅针对 5.10.x、依赖 5.10 的 slab 几何，本机缺 `.text` KASLR slide，且竞态利用有高 panic 风险，与「不重启」硬约束直接冲突。**处置：P1 纯离线形态复核，默认禁止任何动态验证。**

3. **两项按项目方法论完成的硬排除**（结论比"公告没列 4.9"更扎实）：
   - `CVE-2024-46740`（Binder offsets overwrite UAF）：本机 `4.9.227` **从未引入** `6d98eb95b450` 的逐对象增量拷贝重构，漏洞代码路径不存在（§4.1）。
   - `CVE-2022-0492`（cgroup v1 `release_agent`）：本机 `cgroup_release_agent_write()` **确为 pre-fix 形态**（函数体内无任何 capability 检查），但 `CONFIG_USER_NS` 关闭 + 两域无 `CAP_SYS_ADMIN` + 无 mount 权限，公开利用链在本机全部不可达（§4.2）。

4. **必须纠正两个常见误判**（后续 AI 尤其注意）：
   - 不能因为「4.9 已 EOL、不在 2024/2025 公告的修复版本列表」就判定本机不受影响——4.9 是在**漏洞披露前**停止维护，不是已修复。判据必须是 commit 演变 + 本机反汇编形态。
   - 也不能因为「本机某函数是 pre-fix 形态」就判定可利用。`CVE-2022-0492` 就是典型反例：形态成立、可达性不成立。

5. **联网 CVE 排查不应取代 v13 的主线。** v13 的 R0（交接口径同步）+ R1（WLAN 非配置输入可达性矩阵）仍是下一轮首选。本文产出的是「外部候选分诊表 + 一个可选的离线复核靶面」，不是新的研究主线。

**推荐决策：接受 v12.2 收口；把 `CVE-2025-38352` 登记为唯一新增的 P1 纯离线复核项，其余全部排除或降级；不因联网结果启动任何上机动作。**

## 4. 本轮新增的三项形态核对（详细）

### 4.1 `CVE-2024-46740` — Binder "offsets overwrite" UAF：**排除**

**公开事实（已复核）**

- 修复 commit `4df153652cc46545722879415937582028c18af5`，主题 `binder: fix UAF caused by offsets overwrite`（Carlos Llamas，2024-08）。
- `Fixes: 6d98eb95b450 ("binder: avoid potential data leakage when copying txn")`。
- 官方版本边界：引入于 `5.16.3`（`66e12f5b3a97`）、`5.17`（`6d98eb95b450`），backport 到 `5.4.226` / `5.10.157` / `5.15.17`；修复于 `5.4.284` / `5.10.226` / `5.15.167` / `6.1.110` / `6.6.51` / `6.10.10` / `6.11`。**列表不含 4.9 分支**（4.9 于 2020 年 EOL，早于该重构）。
- 补丁只加一行：`if (copy_size && (user_offset > object_offset ||` **+ `object_offset > tr->data_size ||`** `binder_alloc_copy_user_to_buffer(...)))`。
- 漏洞前提：`binder_transaction()` 内**逐对象处理 + 对象之间 raw data 增量拷贝**（`user_offset` / `object_offset` 循环），该形态由 `6d98eb95b450` 引入。

**本机核对（决定性）**

`python tools/kfn.py binder_transaction` 显示本机为**两段式一次性拷贝**，不是逐对象增量循环：

```asm
; 第一次：拷贝 data 区，buffer_offset = 0，size = tr->data_size
0xffffff8008e1f5b4  ldr  x3, [x28, #0x30]
0xffffff8008e1f5b8  ldr  x4, [x28, #0x20]
0xffffff8008e1f5bc  mov  x0, x20
0xffffff8008e1f5c0  bl   binder_alloc_copy_user_to_buffer
0xffffff8008e1f5c8  cbz  x0, #0xffffff8008e1f620        ; 成功后走第二次
; 第二次：拷贝 offsets 区，buffer_offset = ALIGN(data_size, 8)
0xffffff8008e1f620  ldp  x8, x4, [x28, #0x20]
0xffffff8008e1f62c  ldr  x3, [x28, #0x38]
0xffffff8008e1f630  add  x8, x8, #7
0xffffff8008e1f634  and  x2, x8, #0xfffffffffffffff8     ; ALIGN(data_size, 8)
0xffffff8008e1f638  bl   binder_alloc_copy_user_to_buffer
```

这与 `HANDOVER.md` §5.3.1 对 `CVE-2023-21255` 使用的本机片段（`and x9, x8, #~7 ; off_start = ALIGN(data_size,8)`）是同一形态：data 与 offsets 两段固定拷贝，offsets 起点由 `ALIGN(data_size,8)` 定死。对象循环内的 `binder_alloc_copy_from_buffer` / `binder_alloc_copy_to_buffer`（`0x8e1fbb0` 起）是对象头解析与回写，另有 `0x8e1fd78` 一次 `binder_alloc_copy_user_to_buffer` 属 `BINDER_TYPE_PTR` 的 SG 附加缓冲，均**不是** `user_offset/object_offset` 的 raw data 增量拷贝。

**判定**：L1 与 L2 同时不成立——不是"本机已打补丁"，而是**引入漏洞的重构从未进入 4.9.227**。口径与 §5.3.1 一致（按 commit 演变 + 反汇编形态，不按 SPL 或公告日期）。

**范围**：仅排除 `CVE-2024-46740` 这一条特定漏洞路径；不表示本机 Binder 全部代码无缺陷，也不表示其它 Binder CVE 已被排除。

### 4.2 `CVE-2022-0492` — cgroup v1 `release_agent`：**形态 pre-fix，但不可达，排除**

**公开事实（已复核）**

- 修复 commit `24f6008564183aa120d07c03d9289519c2fe02af`，在 `cgroup_release_agent_write()` 开头加：
  ```c
  if ((of->file->f_cred->user_ns != &init_user_ns) || !capable(CAP_SYS_ADMIN))
      return -EPERM;
  ```
- 经典利用链：`unshare(CLONE_NEWUSER|CLONE_NEWNS)` 创建新 user namespace 取得伪 `CAP_SYS_ADMIN` → mount 可写 cgroup v1 → 写 `release_agent` + `notify_on_release` → 内核以 init_ns 全权限执行指定程序。

**本机核对（新发现）**

`python tools/kfn.py cgroup_release_agent_write --calls`：

```text
0xffffff800817f160  bl -> cgroup_kn_lock_live
0xffffff800817f178  bl -> _raw_spin_lock
0xffffff800817f188  bl -> strim
0xffffff800817f198  bl -> strlcpy
0xffffff800817f1a0  bl -> _raw_spin_unlock
0xffffff800817f1a8  bl -> cgroup_kn_unlock
```

函数体内**没有任何 `capable()` / `ns_capable()` / `security_*` 调用**，即**确为 pre-fix 形态**（补丁未 backport）。本机 `CONFIG_CGROUPS=y` 且 `cgroup_release_agent_write` / `cgroup_release_agent` 符号存在，机制层 L2 成立。

**但 L3 三层全部不成立**：

1. `# CONFIG_USER_NS is not set` → 无法 `unshare(CLONE_NEWUSER)` 取得伪 `CAP_SYS_ADMIN`，公开利用链的第一步即断。
2. 现有 `oplus_wifi_service` 域 `CapEff=CapBnd=0x13000`，**不含 `CAP_SYS_ADMIN`(bit21)**；`shell` 域亦无。`SELINUX_DOMAIN_AUDIT.md` 判定"用 CAP_SYS_ADMIN 挂载覆盖"是**双锁**：能力集拿不到 + SELinux 不给 `filesystem:mount` / `mounton`。
3. `# CONFIG_MEMCG is not set`，经典 PoC 使用的 `/sys/fs/cgroup/memory/release_agent` 在本机不存在；现有 cgroup v1 挂载为 init 控制的 `/dev/freezer`、`/dev/cpuctl`，部分 `cgroup.procs` 被 `chown system` / `chmod 0666`，但 `release_agent` 位于 cgroup root 且由 kernfs 权限 + SELinux 管控，现有域无可写证据。

**判定**：排除。**推荐统一表述**："本机 `cgroup_release_agent_write()` 为 pre-fix 形态，但公开利用所需的新 user namespace、`CAP_SYS_ADMIN` 与可写 cgroup v1 挂载在本机全部不可达，故 `CVE-2022-0492` 在本机、本固件、现有两域内不构成可利用路径。"

**重开条件**：出现以下任一具体证据才重开——① 现有域获得 `CAP_SYS_ADMIN` 或 `mount` 权限的可复算反例；② 存在不需 `CONFIG_USER_NS` 的新利用链；③ 发现某个 SELinux 允许写 cgroup root `release_agent` 的域并给出标签证据。

**遗留待核（低优先级，纯离线/只读）**：本机 `cgroup_release_agent_write` 无 capability 检查，意味着**若**某域能凭 DAC root 身份写 cgroup v1 root 的 `release_agent` 且 SELinux 放行，pre-fix 内核会接受。本地物料中没有直接的 `cgroup:file write` sepolicy 规则证据（仅在 `tools/` 下有 `sepolicy_domain_audit.py` / `sepolicy_regression.py` 两个工具，未取回原始 sepolicy 二进制）。此点列为"需重新授权只读上机或离线取 sepolicy 后核验"，**不因该遗留而把本 CVE 提为高优先级**。

### 4.3 `CVE-2025-38352` — POSIX CPU timers TOCTOU / UAF：**唯一新登记的 P1 离线复核项**

**公开事实（已复核）**

- `handle_posix_cpu_timers()` 与 `posix_cpu_timer_del()` 之间的 TOCTOU：已过 `exit_notify()` 的非 autoreap 任务仍可从 IRQ context 调用 timer handling，随后被父进程/ptrace 回收，并发删除无法检测 `timer->it.cpu.firing != 0` → UAF。
- 修复：在 `run_posix_cpu_timers()` 增加 `tsk->exit_state` 检查；上游修复 `5.4.295` / `5.10.239` / `5.15.186` / `6.1.142` / `6.6.94` / `6.12.34` / `6.15.3` / `6.16-rc2`。
- 官方标注 `Affected: 2.6.36`（覆盖 4.9 理论区间）；**4.9 分支无官方修复版本**，原因是 4.9 在漏洞披露前已 EOL（参见 §0 第 4 条，不能据此判定不受影响）。
- **CISA KEV 在野利用**（2025-09-04 收录）；Android 2025-09 公告（SPL 2025-09-05）；公开 PoC `chronomaly`（farazsth98，2026-01）。
- 关键 build-time 缓解：**`CONFIG_POSIX_CPU_TIMERS_TASK_WORK=y` 的内核不需要此修复**（`exit_task_work()` 先于 `exit_notify()`）。

**本机核对**

`python tools/kfn.py --list 'posix_cpu_timer|run_posix_cpu_timers|handle_posix_cpu_timers'`：

```text
0xffffff8008150920 posix_cpu_timer_create
0xffffff8008151160 posix_cpu_timer_del
0xffffff80081500e0 run_posix_cpu_timers      <-- 老命名
0xffffff800814fb30 posix_cpu_timers_exit
0xffffff800814fc10 posix_cpu_timers_exit_group
```

- 本机是**老 `run_posix_cpu_timers` 命名**，符号表中**没有** `handle_posix_cpu_timers`、也没有 task_work 重构痕迹 → 本机**不具备** `CONFIG_POSIX_CPU_TIMERS_TASK_WORK` 这一 build-time 缓解，落在受影响的老路径分支上。
- `run_posix_cpu_timers` 反汇编开头为 `daif`/IRQ 上下文检查 + `tsk->signal` cputimer 字段比较（偏移 `0x760/0x768/0x7e0/0x7e8/0x7f0`）+ `__lock_task_sighand()`；`--calls` 中未见明确的 `exit_state` 早退门。**但这是初步形态观察，不等于已确认本机存在同构竞态**——4.9 的退出时序与 5.10 不同，需逐指令复核（见任务卡 E1）。

**为什么不列为"高优先级突破方向"（L4 不通过的四个具体理由）**

1. **PoC 不通用**：`chronomaly` 明确针对 `5.10.x`，依赖 `sigqueue_cachep` slab 几何、`cross_cache_timers` 双阶段堆布局、`signalfd` 重复与多线程 stall。本机 `CONFIG_SLUB_DEBUG=y`、`# CONFIG_SLAB_FREELIST_RANDOM is not set`、`CONFIG_HARDENED_USERCOPY=y`，4.9 的 SLUB/sigqueue 布局与 5.10 差异大，无适配证据。
2. **缺内核地址前提**：`HANDOVER.md` / `FEASIBILITY_v008.md` 已判定 `.text` KASLR slide 未获得（GhostLock ③ 缺口）。公开 PoC 的内核写原语需要地址基础。
3. **动态验证与安全边界直接冲突**：竞态利用需反复 `timer_create` / 进程 exit / 并发 delete 与堆喷；失败极易 UAF → panic → 必然触发重启，违反「不重启」硬约束，且会作废本次开机的全部地址类结论。
4. **4.9 适配性未证**：官方受影响区间是保守的 `2.6.36` 起标注，4.9 老路径是否真存在 `exit_notify` 后的 IRQ timer 窗口尚未本机逐指令确认。

**判定与处置**：登记为 **P1 纯离线形态复核**（v13 R3 的候选靶面之一，且是"新靶面"而非 KGSL/GhostLock 重做）。**默认禁止任何动态验证**；不编译、不运行 `chronomaly`，不构造竞态，不尝试堆喷。

**升级为"需重新授权"的门槛（全部满足才提交用户决策）**：① 离线确认本机 `run_posix_cpu_timers` / `posix_cpu_timer_del` 确含同构竞态窗口且无 `exit_state` 门；② 出现适配 `4.9/arm64`、不依赖 5.10 slab 几何与 `.text` slide 的原语；③ 有可承受重启的**独立测试设备**（非当前 PCGM00_11_F.16）；④ 用户明确重新授权。任一不满足即停在授权门前。

## 7. 安全与证据纪律（后续 AI 必须继承）

1. **本文不授予任何新设备操作权限。** 全文为纯离线；只读上机亦须单独取得授权。
2. **默认禁止动态验证**：不编译/运行任何公开 PoC（含 `chronomaly`），不构造竞态、堆喷、悬空映射，不并发写 sysctl，不提交 GPU 命令，不 mmap，不重载 WLAN。
3. **不重启设备**；任何可能 panic、GPU fault、WLAN 断链或需恢复的动作不得作为"快速验证"。
4. **不写持久位置**：禁止写 `persist`、刷写/解锁、改分区、关闭或修改安全配置。
5. **pre-fix 形态 ≠ 可利用**；`CVE-2022-0492` 是本轮的反例，报告中不得把两者混同。
6. **EOL ≠ 已修复**；4.9 不在公告修复列表只能说明"无官方修复版本"，适用性必须回到 commit 演变 + 本机反汇编。
7. **负结果必须有范围**：统一写"在本机 / 本构建 / 已审集合内未发现"，不写"绝对不存在"。
8. **结论变更需要新证据**：其它机型、其它 SPL、公开 PoC 或参考项目成功，均不能推翻本机判定。
9. 若另获授权，记录 `boot_id`、`uptime`、上下文、命令、原始返回、临时文件清理与异常日志；失败时先检查探针与 `errno`。
