# F.16 实机基线 + 对 C.17 结论的失效说明 + 下一步路线

- 日期：2026-11-13
- 触发：ADB 实机采集（`k3_info.txt` / `k3_kernel_config.txt` / `k3_采集判读.md`）显示设备运行 **F.16**，与工作区既有 **C.17** 镜像假设不符

---

## 1. 实机事实（一手，不可辩驳）

| 维度 | 值 |
|---|---|
| 型号 / 代号 | `PCGM00` / `ro.product.device=OP4679` / `ro.product.board=sdm710` / `device_family=OPSDM710` |
| 系统 | `ro.build.display.id=PCGM00_11_F.16`；`build.version.release=11`；`sdk=30`；`opporom=V11.1`（ColorOS 11.1） |
| 完整版本 / OTA | `PCGM00_11_F.16_2025032621191106` / `PCGM00_11.F.16_3160_202503262119` |
| 内核 | `4.9.227-perf+`，`#1 SMP PREEMPT Wed Mar 26 16:32:43 CST 2025`，clang 10.0.7 |
| 安全补丁 | `2022-04-05`（google_patch `20220405`） |
| fingerprint | `OPPO/PCGM00/OP4679:11/RKQ1.201217.002/1704167642389:user/release-keys` |
| 构建类型 | `user` / `release-keys` / `debuggable=0` / `secure=1` |
| 启动 | `verifiedbootstate=green`、`flash.locked=1`、`vbmeta.device_state=locked`、`veritymode=enforcing`、`avb_version=1.1` |
| 槽位 | `slot_suffix` 空、by-name 无 `_a/_b` → **A-only**；`system_root_image=true` |
| ADB 身份 | `uid=2000(shell) context=u:r:shell:s0`；`adb root` 失败（production build） |

**设备来源存疑（待核）**：一台 2019 年的 K3 出现 **2025-03 构建的 Android 11 F.16**，且带 `ro.boot.realme.*` 属性，存在"同平台融合包/售后重刷/跨机型移植"的可能。但它 `release-keys + locked + green + verity enforcing`，属**真实 OEM 签名构建**，不是随便的第三方 ROM。后续取固件必须以本机 fingerprint 尾号 `1704167642389` 精确匹配。

## 3. 仍然有效 / 新增利好（来自实机 config + slabinfo）

**仍然有效**
- 平台 `sdm710`、`CONFIG_USER_NS=n`（CVE-2021-22555 标准链仍被阻断）、BL 仍锁（解锁闸门仍是令牌）。
- `CONFIG_RANDOMIZE_BASE=y`、`CONFIG_ARM64_PAN=y` / `UAO=y`、`THREAD_INFO_IN_TASK=y`、`UNMAP_KERNEL_AT_EL0=y`。
- `/proc/kallsyms` 不可读 → **KASLR 必须运行时泄露**（结论不变，甚至更强：直接 Permission denied）。
- 无 KASAN/UBSAN/DEVMEM/PROC_KCORE/KPROBES → 无内核内存接口可用。

**新增利好（对 UAF 利用）**
- `CONFIG_SLAB_FREELIST_RANDOM` **未开**；`CONFIG_SLUB=y` 且 `SLUB_DEBUG=y`。
- **`/proc/slabinfo` 可读** → 可观测 `kmalloc-*`、`cred_jar`(objsize 192)、`task_struct`(3840)、`filp`(320) 等真实缓存，堆喷可量化。
- 无 PAC / CFI / ShadowCallStack（4.9 时代），少一层绕过。

**关键缓存（实测 objsize，供后续利用对齐）**：`cred_jar=192`、`task_struct=3840`、`filp=320`、`kmalloc-256/512/1024`、`vm_area_struct=184`、`dentry=192`。

**新约束**：SPL 推到 2022-04-05，2021 年前公开 LPE 大概率已修；候选 CVE 需按 4.9.227 重排。

## 4. 下一步路线（按 ROI 排序）

### Step 0（硬前提，最先做）：取得 F.16 的 boot.img / 内核
锁定状态下**无法**从设备 dd 分区、也无 `/dev/mem`、`/proc/kcore`。**只能靠下载官方固件包**取得 boot.img：
- 目标包按 `PCGM00_11_F.16` / fingerprint 尾号 `1704167642389` / OTA `PCGM00_11.F.16_3160_202503262119` 精确匹配。
- 渠道优先级：① OPPO 官方 OTA/固件接口（复用我们已有的 `coloros.com/api/.../romList` 抓取与 `tools/ozip_range_extract.py` 局部提取法，先查 productId 下是否已含 F.16）；② 官方线刷包（OFP，需授权账号，多数情况不可得）；③ 第三方固件库（交叉核对 MD5/构建时间，防错包）。
- 交付：`firmware_F16/`（boot.img、vbmeta.img、内核解出），核对 `ro.build.kernel.id=4.9.227` 与 `fingerprint`。

### Step 1（并行，低成本高回报）：先试官方「深度测试」解锁
- 装 `com.coloros.deeptesting`（本机未装），在**支持深度测试的出厂版本**上申请；受理则 → BL 解锁 → Magisk **持久 root**，**严格优于临时 root**，可省掉全部漏洞开发。
- 风险：F.16 未必在深度测试支持版本内；K3 的申请条件（购机满 3 月、本机账号登录 60 天、每月 15 日审核）需逐项核。
- 判定：若受理 → 直接转 Magisk 路线，**终止临时 root 研究**。

### Step 2（研究线，Step 0 之后）：F.16 的 GhostLock 可移植性重评
- 复用已写好的工具链（`tools/kallsyms_recover.py` + `solve_names.py`），把 `PATH` 指向 F.16 的 `kernel.decompressed` 重跑，得到 **4.9.227** 的 `remove_waiter`/`rt_mutex_start_proxy_lock`/`futex_requeue` 等偏移。
- 重点确认 4.9.227 是否 backport 了 GhostLock 修复（预期：否，修复在 2026）；并核对 Android 11 是否引入额外加固。
- 结合可读的 `/proc/slabinfo` + `FREELIST_RANDOM=n`，评估 UAF→读写原语的堆喷可行性（比 C.17 环境更友好）。

### Step 3：仅当 Step 1 不受理 且 Step 2 判定可做
- 再做利用开发（工作量按前评估 15–25 人日量级，且仅得临时 root）。

---

## 5. 一句话建议

**先做 Step 1（试深度测试，1 小时，可能直接一步到位拿持久 root），同时 Step 0 去下 F.16 固件。** 在拿到 F.16 内核之前，任何"GhostLock 能不能打"的判断都是对错版本的猜测。
