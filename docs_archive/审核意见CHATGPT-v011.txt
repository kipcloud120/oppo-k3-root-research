二、我建议的后续优先级
P0：重新研究内核栈地址的信息来源（GhostLock ③）
我认为最值得优先投入
K3 当前已经有 xattr 栈载体，也已经解决相关数据布局的静态几何问题。现在缺少的是：如何可靠定位持有 stale waiter 的那个内核线程的栈基址。

已有证据说明：
- CONFIG_VMAP_STACK 没有启用。
- 栈使用线性映射区域的页。
- futex key 不含内核栈地址。
- perf_event_paranoid=3，传统 perf 路线受限。
- 参考的 USENIX'25 TLB 栈侧信道依赖 VMAP_STACK，本机条件不符。
  GitHub+1
因此，下一轮不应该重复研究 futex 时序或直接套用 VMAP_STACK 侧信道。

更合理的是开展一次独立的只读审计：检查当前内核和厂商驱动有哪些面向低权限调用者的任务信息、栈信息或异常诊断接口，确认是否真正暴露当前线程的内核栈地址。

停止标准： 找不到任何低权限可达、能够提供栈地址或等价地址关系的接口，就暂时关闭这一子方向，不继续堆叠理论假设。
P1：寻找独立的内核对象地址锚点（GhostLock ②）
有研究价值
这条路线不是继续修补 M2，而是寻找与 M2 不同的地址来源。

v10 已经证明，单凭 mm slab 与 skb 的时间先后不能可靠预测地址。还要考虑一个结构差异：
- mm_struct slab 扩容来自 SLUB。
- 16 KB skb data 走 kmalloc_large，直接使用 buddy 分配。
- 两者虽然都可能涉及 order-2 页面，但不保证处在相同的分配域或分配序列中。
  GitHub+1
后续真正值得寻找的是独立、可验证的内核对象地址来源，以及能否证明对象结构满足 rt_mutex 的约束。

不建议继续使用“同大小分配必然相邻”“分配时间接近所以物理地址接近”这样的推断。

这里应该有一个非常严格的证据门槛：地址来源必须可以独立验证，不能仅靠另一个同样依赖 allocator 假设的地址公式。
P2：独立审计 Qualcomm / OPPO 内核驱动的漏洞面
值得开新分支
我认为这是 GhostLock 之外，最值得保留的替代路线。

目前项目已经审过 KGSL、Binder、FastRPC 和 /dev/diag 等面；其中 KGSL 路径会触发内核 panic，FastRPC 对当前 Wi-Fi root 域封闭，两个 Binder CVE 也没有形成可用原语。
GitHub+1


但项目的判定范围始终是 PCGM00 F.16 的具体二进制，不是对整个 SDM710 平台所有厂商驱动的完备证明。

建议新开一份驱动安全面清单：
审计对象	研究目标	优先度
WLAN 驱动及配置解析器	查找输入长度、状态机和内存生命周期问题	高
Qualcomm 共享内存和诊断接口	检查当前固件中实际存在的解析路径	中
其他实际开放的字符设备	查清 shell / Wi-Fi root 的实际可达范围	中
已知 CVE 对照	以 K3 的真实构建、函数和修复状态逐一确认	高

其中有一个容易被忽略的线索：项目曾确认 /mnt/vendor/persist/wlan/WCNSS_qcom_cfg.ini 是实际存在的文件，但之前对 root 脚本的消费链分析已经证明它不构成直接提权路径。剩下的 WLAN 驱动配置解析才是内核研究问题。可以先做离线解析器审计，不需要修改 persist 文件。
GitHub+1


这条路线的价值在于：即使没有找到 GhostLock 地址原语，也可能出现一个不依赖 GhostLock 的新缺陷。
P3：完成 DCI 的剩余 R1、R2
低优先级、有限工作量
DCI 主路径已经有明确的静态否证。剩余项目是：
项目	内容	我的判断
R1	extract_dci_ctrl_pkt 控制状态与 mask 一致性	可以做一次离线闭合
R2	两条 non-apps 入口的来源和前置长度检查	有证据显示共用已审分派器，但入口仍未逐路径确认
R3	u16 长度字段的功能边界	不值得作为安全研究主线

这三项不应继续占据主要设备测试时间。报告本身也明确将它们列为残余逻辑/来源问题，而不是已确认的漏洞。

三、哪些方向现在应该停止投入？
我会明确冻结以下工作：
方向	决定	原因
M2 固定时间 delta	停止	已有两轮真机否证
重复扩大 futex 扫描	停止	M1 已闭合

四、我会怎样安排下一版 v11？
我的建议是不要再做一个单线 GhostLock 版本，而是把项目分成三个相互独立的工作流：
OPPO K3 后续研究路线 v11
Track A：内核栈地址可观测性
P0
目标：确认是否存在独立于 futex 的栈地址信息来源。

产出：可达接口清单、数据来源、地址精度及证据等级。

Track B：可验证的内核对象地址
P1
目标：寻找不依赖时间邻接的地址锚点。

产出：地址证据、对象类型验证、适用条件。

Track C：独立驱动漏洞面
P2
目标：覆盖尚未完整枚举的 Qualcomm / OPPO 驱动接口及配置解析面。

产出：按实际固件匹配的漏洞候选清单。


所有工作先做离线、只读分析。只有出现明确的新假设和可证伪判据后，才考虑设备验证。

我的实际执行顺序是：
1. 先完成 Track A 的只读接口枚举，因为它直接解决 GhostLock 的③类缺口。
2. 并行完成 Track C 的 WLAN 驱动静态审计，给项目保留一个独立于 GhostLock 的可能性。
3. Track B 只有在找到新的地址观察依据后才扩大投入。
4. DCI 的 R1/R2 用一轮有限审计收尾。
五、一个关键判断
目前项目最大的问题已经不是缺乏技术积累，而是大部分已知路径都存在明确的证据边界。

我不建议为了让 v11 看起来有突破，再重复跑一次 KernelSnitch，或者换一组喷射参数继续试 M2。

真正可能改变结论的只有两类新证据：
- 可复现的内核栈地址信息来源；
- 一个独立、可验证、结构上适合的内核对象地址来源，或者不依赖当前 GhostLock 地址条件的新内核缺陷。
其他结果即使有实验数字，也未必会推进到 ROOT。

所以我的最终建议是：v11 应以“寻找新原语”为主题，而不是“继续优化已有 PoC”。 当前可用 ROOT 仍然是 NO-GO，不应因为 M1 闭合或 DCI 静态审计完成而改变。
