针对 OPPO PCKM00 的 GhostLock 移植项目找到的内核地址泄露思路有哪些值得参考的？

我检查了 PCKM00 项目的 slide.c、fops.c 和分析报告。最值得参考的不是某一个单独的内核地址泄露 API，而是它把“可控内核写入”转换成“用户态可读取的地址”，再用真实函数指针交叉验证 KASLR 基址的两阶段设计。

这点会改变我们对它的评价：PCKM00 项目的 boot_id 方案并非一个可以脱离 GhostLock 利用原语、单独移植的普通信息泄露技巧。它依赖前面的内核内存控制能力。
GitHub+2

1. 第一优先级：boot_id 指针回读（最有参考价值）
值得重点研究
PCKM00 项目在这里的设计相当巧妙。

它利用了两个不同的内存地址空间概念：
- 内核镜像的虚拟地址：会受到 KASLR 影响。
- 内核线性映射（Direct Map）地址：在已知物理内存布局时，可以通过物理地址关系推导。
它的 target.h 定义了 PCKM00 的物理内存布局参数，包括：
参数	PCKM00 的定义
PAGE_OFFSET	0xffffff8000000000
PHYS_OFFSET	0x80000000
内核物理加载地址	0x88080000

利用这些目标参数，项目可以建立内核镜像符号和线性映射地址之间的关系。
GitHub+1


随后，它选择了一个有意思的用户态可读位置：/proc/sys/kernel/random/boot_id。

其思路是：
1. 通过已经建立的内核内存操作能力，控制内核数据结构所产生的写入效果。
2. 让一个已知内核地址的信息反映到 boot_id 的底层数据中。
3. 从普通用户可读取的 procfs 接口获得这些字节。
4. 根据对应内核符号的位置关系，恢复运行时内核基址。
因此，它不是简单地发现 boot_id 自己会泄露内核指针，而是把一个受控内核内存操作转化为可从普通文件接口读取的地址信息。
GitHub+2

对 K3 有什么价值？
K3 当前的问题是：
- KASLR 开启。
- /proc/kallsyms、/proc/kcore、dmesg 等观察面不可用。
- GhostLock 的 xattr 栈覆盖候选已经找到，但 fake waiter 的部分字段需要非零内核地址。
这与 PCKM00 项目面对的问题高度相似。
GitHub+1


但需要注意：PCKM00 使用的是自身的物理内存布局和利用载体。K3 是 4.9.227，不能直接复用它的物理映射常量。

我的判断：这是值得研究的设计模式，但要先确定 K3 自己的物理内存布局能否提供可靠的地址锚点。
2. 第二优先级：KernelSnitch 的 futex 哈希侧信道
值得交叉研究
这是我认为此前 K3 分析中值得特别关注的一项。

PCKM00 项目集成了 KernelSnitch。它的思路不是直接读取 /proc 中的地址，而是利用 futex 哈希桶的行为差异，间接判断内核对象所在地址。

从代码看，它主要做了两件事：
- 利用一组 futex 地址之间的哈希碰撞关系，建立可识别的哈希桶特征。
- 通过内核处理时间的差异，筛选与实际 mm_struct 地址相匹配的候选位置。
最终，它得到的是内核线性映射区域里的 mm_struct 地址，而不只是一个 KASLR 文本基址。
GitHub+1


这里需要区分两种地址：
地址类型	KernelSnitch 的作用
内核堆对象 / 线性映射地址	可以帮助定位
内核代码段运行基址 / KASLR slide	不能直接等同于已经得到

这对 K3 有特别的研究意义。

K3 的 GhostLock 当前要求 fake waiter 中的 lock 和 RB-tree 链接具有有效的非零内核地址。KernelSnitch 这种对象地址侧信道，理论上可能为进一步分析内核对象布局提供信息。

不过，它依赖 futex 哈希实现、mm_struct 尺寸、SLUB 分配布局和实际 CPU 时序。PCKM00 针对 4.14.180 做了适配，K3 的 4.9.227 不能直接照搬。
GitHub+1

3. 第三优先级：ashmem_fops 函数指针交叉验证
适合作为验证思路
PCKM00 项目还没有满足于只从 boot_id 得到一个地址。

它继续检查 ashmem_fops 中的多个函数指针，例如：
- open
- ioctl
- mmap
- release
根据这些函数对应的已知符号偏移，检查它们是否共同指向同一个运行时内核基址。

其意义在于：

一个地址看起来像内核地址，不等于它一定是正确的 KASLR 结果；多个已知函数指针应该能相互验证。

源码中的 leak_kernel_base() 正是采用这种交叉确认方式。
GitHub


它还利用 configfs 的 bin 文件操作路径建立内核数据读写能力。这部分与单纯的信息泄露不同，是后续内核内存操作的基础。
GitHub+1


K3 可以借鉴的是：
- 研究本机 ashmem 的实际 file_operations 布局。
- 检查 configfs 对应的内核实现和编译配置。
- 设计多个独立符号之间的一致性校验。
但 K3 是 4.9，必须以 F.16 的实际内核镜像为准，不能直接使用 PCKM00 的函数偏移。
4. 哪些部分不能直接移植？
这里有一个非常重要的差异。

PCKM00 的 GhostLock 利用链使用 pselect 的 fd_set 作为 fake waiter 的载体。K3 项目自己的反汇编已经发现，K3 的 select/pselect 路径栈深度不满足要求，不能照搬这条载体路径。

K3 后来找到的是三条 xattr 栈覆盖候选：
路径	项目结论
fgetxattr	载体候选成立
getxattr	载体候选成立
setxattr	载体候选成立

但这三条路径仍然受到 fake waiter 指针字段约束。
GitHub+1


所以，我认为最有意义的研究问题是：
PCKM00 的物理地址锚点和对象定位思路，能不能与 K3 已经找到的 xattr 栈载体结合？

这是一个研究假设，目前没有证据证明已经成立。
5. 我建议 K3 项目这样安排下一轮审计
先做离线验证，不直接运行完整 PoC。
优先级	审计内容	需要回答的问题
P0	K3 的物理内存布局	能否独立确定 PHYS_OFFSET、线性映射范围和内核物理加载位置？
P0	nfulnl_loggers / sysctl_bootid	F.16 内核是否包含相应符号，实际数据布局是否符合利用思路？
P1	KernelSnitch	4.9.227 的 futex 哈希实现及 mm_struct 布局是否支持类似的对象地址分析？
P1	ashmem/configfs	本机是否具备对应数据结构和兼容的读写接口？
P1	地址编码约束	可确认的地址是否满足 K3 xattr 载体对非零字节和 RB-tree 字段的要求？

还有一项风险必须提醒：PCKM00 项目的 README 自己报告，完整 PoC 在其目标设备上约有 97% 的概率触发内核 panic。它是研究参考，不适合直接在 K3 上试跑。
GitHub


最终判断
我认为最值得借鉴的是两项技术的组合：
1. KernelSnitch：提供内核对象地址和内存布局线索。
2. boot_id 指针回读：把受控内核内存操作转换成用户态可读的地址信息。
ashmem_fops 则适合用作后续地址验证和内存操作研究。

尤其重要的是：K3 已经解决了符号恢复问题，不需要再花精力重复提取符号；真正缺失的是运行时地址知识。 K3 的 vmlinux 已恢复出 123,784 个符号，但符号偏移不等于 KASLR 后的运行时地址。
GitHub+1


所以我会把 PCKM00 项目作为 K3 GhostLock 专项研究的重要参考，重点放在它的 slide.c、util.c 和 kernelsnitch 子目录，而不是整个 PoC 的利用代码。
