1. Track A：内核栈地址泄露，基本应该正式关闭
这是 v11.6 最重要的负结果之一。

此前项目怀疑可能从 /proc、内核栈回溯或 ARM64 的寄存器信息中找到 W 线程的内核栈地址。v11.1–v11.6 把这些假设逐步落实成了实际检查。

关键结果：
检查	最新实测
/proc/self/stat	kstkesp=0、kstkeip=0
/proc/self/stack（shell）	SELinux 拒绝
/proc/self/stack（Wi-Fi UID 0）	可以读取，但当前运行任务返回空
/proc/1/stack	无可用输出
/proc/self/wchan	只有符号名或 0
/proc/kallsyms	SELinux 拒绝
CapEff	0x13000，不包含 CAP_SYS_ADMIN、CAP_SYSLOG

这里有个特别重要的更正：/proc/self/stack 在 Wi-Fi root 域实际上能够打开，但输出的格式是 %pK 门控的返回地址，不是 SP，也不指向线程栈页。不能把它误写为完全无法访问，也不能把它误认为栈地址泄露。
GitHub+2


另外，panic_on_oops 并没有得到实测值，两个可用域都被 SELinux 拒绝读取。v11.5 已经正确撤回此前“推断为 1”的表述。

我的结论：③ 类地址来源，在当前枚举的低权限接口范围内没有找到。GhostLock 的栈地址路线应停止常规投入。

这不代表世界上不存在任何其他栈地址泄露，只代表当前已审计的可达接口没有提供证据。

3. Track C2：KGSL 是目前最值得推进的路线
新的第一优先级
我认为这是 v11.6 最重要的正面结果。

先看设备可达性：
- shell（UID 2000）可以打开 /dev/kgsl-3d0。
- DRAWCTXT_CREATE 已经成功。
- 一个 KGSL ioctl 在当前设备上也成功返回 0。
这意味着 KGSL 并不是只能从理论上分析的驱动，而是一个当前 shell 能实际到达的内核接口。
GitHub+1

长度安全维度已经基本闭合
v11.3–v11.5 检查了：
- 54 个 kgsl_ioctl 入口；
- 14 个用户态与内核态数据拷贝点；
- CONST、REG 长度来源；
- legacy 和 Adreno ioctl 分派逻辑。
最终结果是 14/14 有界。

其中一个很重要的实现细节是：legacy 和 Adreno 路径使用 min(cmd_size, entry_size)，不是要求两个长度严格相等。

项目还用设备差分测试纠正了自己最初对这个逻辑的误读。这意味着长度相关的简单越界路线已经明显降温。
GitHub+1

真正还没有审的是对象生命周期
v11.6 明确列出了这些未覆盖范围：
子方向	未解决的问题	优先级
gpuobj_free	ID、对象引用及销毁状态的一致性	最高
gpuobj ID 映射	对象释放与重新分配时，引用是否仍然正确	高
sparse_bind	索引区间及资源状态一致性	高
refcount	引用持有、释放和错误路径是否配对	高
并发 ioctl	多线程状态变更与资源清理之间的竞态	中

这些方向与历史 KGSL 漏洞更常出现的对象管理问题相符。v11.6 也明确指出，14/14 的长度安全结果并不能证明对象生命周期是安全的。
GitHub+1


我赞同项目倾向先审 gpuobj_free 的 ID 生命周期。

这条路线的优势是：
1. 设备可达性已经有实测。
2. 内核模块和符号资料已经齐全。
3. 简单长度错误已经排除，可以把研究集中在状态管理上。
4. 这条路线不依赖 GhostLock 的 fake waiter，也不要求先找到内核栈地址。
但目前没有确认 UAF、double-free 或其他漏洞。它是一个值得深入审计的攻击面，不是已经发现的提权漏洞。
4. GhostLock：应该从主线转为冻结状态
结合 v10 和 v11.6，我会重新评估三种地址需求：
地址类型	当前状态
① mm_struct 线性映射地址	已闭合
② 可控、结构合法的 rt_mutex 堆地址	未解决
③ W 线程内核栈基址	现有接口已枚举否证

M2 的时间邻接路线已经被真机数据否证，而 ③ 又完成了更深入的接口枚举和设备复核。

这使 GhostLock 的剩余工作收敛到 ②：寻找独立的内核对象地址锚点。

但是，目前没有新的证据支持恢复固定 delta、继续 futex 扫描，或直接拿 PCKM00 的地址公式移植。

因此，我建议：

GhostLock 保留理论研究记录，但从 v12 的优先工作列表中移除。

只有出现新的、可独立验证的内核对象地址来源时，才重新打开。
5. v12 研究路线建议
我会将接下来的优先级调整为：
OPPO K3 v12 研究优先级
P0：KGSL 对象生命周期审计
主线

重点覆盖 gpuobj 生命周期、ID 管理、refcount 和 sparse_bind 状态一致性。

目标是先形成完整的静态状态机和不变量表，确认是否存在可被用户触发的生命周期错误。

P1：WLAN 模块其他输入面
条件性

不再研究不可达的 persist 配置输入，转而确认 shell 经现有接口能够触发哪些模块功能，并审查这些真实输入路径。

只有确定输入来源和调用权限后，才深入检查解析代码。

P2：剩余 vendor 模块枚举
次要

/vendor/lib/modules/ 目前有 41 项，但只有 qca_cld3_wlan.ko 已做深度分析。应先确定模块的实际加载状态、调用入口和 shell 可达性，再决定是否获取与审计。

冻结：GhostLock ②/③
暂停

不重复 M1、M2，不重复扫描已经否证的栈接口。新信息来源出现时才重开。

我会给 KGSL 设置三个阶段性里程碑
里程碑	应交付的证据	停止条件
K1：对象状态图	create/import/free/release 的状态及引用关系	所有对象销毁路径均有明确所有权
K2：索引与生命周期	ID 映射、索引边界、引用计数不变量	无可达的过期引用或错误状态转换
K3：并发一致性	锁、引用和清理路径的静态审计	未发现可触发的并发状态错误

这比一开始直接做真机压力测试更加合理。尤其之前 KGSL 的已知 CVE 命中可能导致 panic，应该先完成离线状态机分析，再决定是否有必要验证动态行为。

最终判断
v11.6：研究重心应该转移
GhostLock： 两类剩余地址条件仍未解决，栈地址路线基本关闭。

WLAN 配置解析： 模块已取得，但当前输入路径不可达。

KGSL： 长度维度 14/14 有界，真实 shell 可达，对象生命周期及并发仍未审计。

整体 ROOT： 受限 UID 0 已达成，可用 ROOT 和持久 ROOT 仍为 NO-GO。

我的明确建议是：v12 将 KGSL gpuobj_free、ID 生命周期和引用管理设为唯一主线，其他方向只做有限补充。

这是当前已有证据最充分、前置条件最少、又不依赖 GhostLock 地址缺口的研究方向。
