我确认了这次确实是默认 main 分支的 v10，不再是之前读取到的 v5。主要更新集中在 HANDOVER_RESUME.md、HANDOVER.md §49–§50、CLOSURE.md 和 M2 示踪探针。

我的核心判断：v10 的研究方向没有整体走错，但它已经给出了一个明确的止损信号——不要再把 PCKM00 的“mm 地址 + 时间邻接 + 固定 delta”当作 K3 的默认可移植方案。

不过，我发现 v10 对“喷射规模 K 与地址散布无关”的结论说得比现有数据所能支持的更强，下面会解释。
1. 一个重要进展：M1 现在确实闭合了
v10 沿用了 v8/v9 已经完成的验证，而不是重新猜测一个内核地址：
- v8：两套独立数据恢复出唯一 mm_struct 候选，19/19 与 26/26 hit 同桶。
- v9：在同一个进程、同一个 mm 不变的情况下，用互斥预测地址集做了实测验证。
- v9 的预测集合为 32/32 热命中，冷对照 32/32 冷命中，没有观测到误报。
这一步很关键，因为它把 G2 从“离线搜索找到了看似合理的地址”推进到了“恢复的地址能够预测未参与搜索的地址行为”。
GitHub+2


所以，现在不应该继续把主要精力放在反复证明 futex oracle、重复扫描 mm_struct，或者继续调整 G2 的旧搜索窗口。

M1 已经是可复用的工具，不再是当前瓶颈。
2. M2 实验：否定了一个具体假设，但还不能说 K 完全没有影响
v10 的方法是把新建进程的 mm_struct slab 页当作分配流的示踪点：在不同步骤之间保留进程、喷射 AF_UNIX 数据包，再恢复示踪进程的 mm 地址，比较相邻示踪页的地址差。

这个设计有价值，尤其是它修正了两个重要的内存结构认识：
- mm_struct 对象为 896 字节，每个 slab 有 18 个对象，占 4 页，即 order-2。
- 16KB 的 skb data 走 kmalloc_large，也是 order-2，直接向 buddy allocator 请求内存，而不是进入普通 SLUB kmalloc 缓存。
- shell 的 SO_RCVBUF 受到 rmem_max 限制，每个 socket 实际只能容纳约 12 个 16KB 包。

一个我认为值得单独复算的数字关系
我用 run2 中可恢复的 T1 和 T3 地址计算了跨越两次 K=768 喷射的合并距离：
\[
d_{13}=-137634\ \text{个 order-2 块}
\]

run2 的 d01 是 −70355 块，因此：
\[
d_{13}-2d_{01}=3076
\]

而两次喷射的包数合计为 1536，3076 恰好接近其两倍（3072）。这不能证明喷射造成了可预测的地址位移，因为 d01 与 d34 的背景距离本身就相差很大，说明基准分配流并不稳定。

但这个数值关系值得核对：每个成功发送的数据包究竟对应多少个 order-2 buddy 分配？是否存在额外分配或统计口径差异？当前文档没有解释这个关系。它不应该被简单归入“K 无关”。

3. 我发现的四个审计问题
这些问题不会推翻 v10 的所有实验，但会影响结论的严格程度。

① “9/9 唯一解”应增加程序级唯一性断言。

m2_tracer_analysis.py 的 recover_mm() 会对 found 排序，然后直接返回 found[0]。它没有要求 len(found)==1，也没有在结果文件里完整记录所有达标候选的数量和第二名分数。

所以文档所称的唯一解可能是正确的，但不能仅凭这个分析函数的返回值证明唯一性。建议输出 candidate_count、最高分、次高分，并在声称唯一解时强制检查只有一个达标候选。
GitHub+1


② dummy fork 的实际成功次数没有记录。

探针尝试每步创建 40 个 dummy 进程，但 fork 失败时会退出循环；后续日志仍然写入 N_DUMMY，也就是 40，而不是实际成功数。

这一点非常重要，因为整个示踪设计依赖于耗尽 mm_struct slab 的空闲对象，再让后面的 tracer 触发新的 order-2 slab 分配。建议记录成功数、失败 errno，并保留 dummy 前后及 tracer 创建后的 slabinfo 快照。
GitHub+1


这里有一个积极因素：run2 的 postdummy 元数据多次显示 active==total，说明当时没有空闲的 mm_struct slab 对象；而 postspray 的 mm_struct 数量没有变化。这对“后续 tracer 需要新 slab”的设计提供了支持。但最好通过 posttracer 快照把因果关系直接记录下来，而不是依赖下一步的累计变化来推断。
GitHub


③ 两种 order-2 分配不等于同一分配序列。

这是结构层面最容易被忽略的问题。

mm_struct 的 order-2 页面来自 SLUB slab 扩容；16KB skb data 则来自 kmalloc_large 的 buddy 分配路径。它们最终都可能请求 order-2 页面，但这不等于它们必然使用相同的 zone、迁移类型、GFP 标志或分配缓存。

所以，“大小同阶”可以让 mm slab 成为有价值的分配流观察对象，却不能单独证明 mm slab 和 skb data 在同一个可预测的分配队列里按顺序出现。

这也是为什么我认为 v10 的地址示踪结果应当被理解为对简单时间邻接模型的强否证，而不是对 buddy allocator 所有邻接关系的彻底否证。

④ README 和 CLOSURE 的版本摘要还没完全统一。

README 已经加入 v10 结论，但状态表仍然使用 v8 口径；CLOSURE.md 的标题和版本表也仍然停留在 v8，虽然正文已经追加了 v10 结果。建议统一摘要中的版本和状态，避免下一位审阅者误用旧结论。
GitHub+2

4. 是否应该继续 GhostLock？
我的建议是：保留 GhostLock，但正式关闭“mm 锚点 + buddy 时间邻接 + 固定 delta”这条子路线。

下一阶段不应该继续做更多类似的 futex 扫描。M1 已经足够成熟，重复扫描的收益很低。

应该把工作拆成两件事：
方向	建议
KernelSnitch / M1	冻结为已验证的地址观测工具
固定时间 delta	在当前 K3 内存状态下判定为不成立
buddy split-pair	只做一次离线分配顺序审计，不凭理论推导宣称成功
AF_UNIX skb 落点验证	缺乏独立观测 oracle，暂不追加大规模真机实验
fake waiter 所需合法 rt_mutex 地址	仍是关键缺口
内核栈基址	仍没有有效泄露来源

这里还有一个可以纳入审计的变量：M2 探针是在 shell 权限下执行的，报告明确指出 shell 的接收缓冲区受到 rmem_max 限制。但此前项目记录的 Wi-Fi 受限 root 能力集 0x13000 包含 CAP_NET_ADMIN。这条身份的子进程能否保留该 capability，以及 OPPO SELinux 是否允许相应 socket 缓冲区操作，目前需要单独核实。即便能提高喷射量，也不等于能得到 skb 的真实内核地址。

一、目前值得考虑的五条路线
路线 A：内核栈地址泄露

值得优先研究
③ 类地址
直接针对 GhostLock 当前 xattr 栈载体需要的 W 线程内核栈基址。

K3 的 CONFIG_VMAP_STACK 未启用，因此线程栈使用线性映射区的内存。但这不意味着普通用户态能从 mm_struct 地址推导线程栈地址。

已知的限制包括：

perf_event_paranoid=3，perf 路线已实测排除。

futex key 不包含内核栈地址。

之前参考的 TLB 栈侧信道依赖 VMAP_STACK，K3 不满足条件。

/proc/kallsyms、/proc/kcore、dmesg、pstore 等观察面也受到限制。

依据：GhostLock 地址分类与 perf 实测。
GitHub
+2

路线 B：直接获得可控内核对象的地址

值得研究
② 类地址
不再依靠 mm 与 skb 的时间邻接，而是寻找独立的地址锚点。

这里的核心不是再扩大 skb 喷射规模，而是研究是否存在能够暴露内核对象指针的合法接口，以及能否确认某个对象确实是符合结构要求的 rt_mutex。

SLAB_FREELIST_RANDOM 未启用，有利于研究同一 slab 内的分配顺序；但没有堆页地址锚点时，确定的对象布局仍然不能提供对象的绝对地址。

依据：§46.7 和 §50.3。
GitHub
+1

路线 C：重新设计 GhostLock 的利用前提

高难度
目前分析围绕 fake waiter 指向一个合法 rt_mutex 展开。可以重新审查这个利用原语是否存在其他实现方式，而不是把“构造假锁对象”作为唯一前提。

研究目标是判断能否利用已有合法内核对象或不同的对象生命周期条件，减少对未知内核指针的依赖。

这是内核机制研究，不代表目前已经找到可行替代方案。

路线 D：寻找独立的内核信息泄露或内存缺陷

值得补审
这一条不依赖 GhostLock，可以为路线 A、B 提供地址信息，也可能独立构成临时 ROOT 的研究入口。

目前能明确指出的未完成审计对象是 /dev/diag 的 DCI 报文解析子树。项目已经检查了入口函数和 55 个数据拷贝点，但没有穷尽 DCI 内容解析逻辑。

这只是尚未审完的攻击面，不代表已经发现漏洞。

路线 E：非漏洞路线

条件性方案
如果将来愿意放宽“不解锁 Bootloader”的约束，可以单独重新确认 OPPO 官方解锁、工程测试和售后授权流程。

这与临时 ROOT 漏洞研究不是同一个目标，也不能假定 PCGM00 当前固件一定允许官方解锁。

二、我认为最值得投入的，其实是 A 和 D 的组合
原因在于，这两条路线可以互相提供价值。

目前 GhostLock 真正缺少的是：

一个可用于 xattr 栈载体的当前线程内核栈地址；

或者一个可控、内核可写、结构合法的 rt_mutex 地址。

这两者是不同的目标，但都可以由独立的信息泄露或内核缺陷提供。

因此，DCI 解析器审计具有双重价值：它即使不能独立完成提权，仍可能发现能够暴露内核地址的接口。

这里我想特别纠正一个容易产生的误解：

/dev/diag 入口层审计通过，不等于整个 diag 驱动的数据解析逻辑已经审计通过。

项目自己的记录也明确保留了 DCI 解析子树这一未完成项。

mm_struct 地址 + 分配时间邻接 + 固定 delta。
